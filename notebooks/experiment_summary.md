# สรุปผลการทดลอง — Stage 2: Vertebral Fracture Classification

> เอกสารนี้สรุปการทดลองของ Stage 2 (การจำแนกความรุนแรงของกระดูกสันหลังยุบ
> ตามเกณฑ์ Genant) พร้อมผลลัพธ์ ข้อค้นพบ และข้อจำกัดที่ต้องพิจารณา

**อัปเดตล่าสุด 25/08/2026 · การทดลองสะสม 100 รัน · แบ่งเป็น 3 ภาค**

| ภาค | หัวข้อ | เนื้อหา | ความน่าเชื่อถือของตัวเลข |
|---|---|---|---|
| 1 | 1–8 | โครงงาน ข้อมูล และการทดลองพื้นฐาน (bbox/masked, RAD-DINO, metadata, binary, 3class, B4) | seed เดียว · โปรโตคอลไม่ตรงกันทุกแถว |
| 2 | 9–17 | preprocessing, augmentation, ฟีเจอร์เรขาคณิต, สูตรช่องสี | seed เดียว · early stopping ไม่เสถียร |
| **3** | **18–31** | **กวาด preprocess/augment เต็มรูปแบบ, การขยายข้อมูล, โจทย์ binary + วิธีทำสมดุล** | **>= 2 seed ทุกจุด · โปรโตคอลเดียวกันหมด** |

**อ่านอะไรก่อน**: ถ้าต้องการตัวเลขไปเขียนเล่ม ให้ใช้ภาคที่ 3 เป็นหลัก
ภาคที่ 1-2 มีข้อสรุปที่ถูกพิสูจน์ภายหลังว่าผิดอยู่ 2 จุด (มีป้าย ⚠️ กำกับไว้ที่
หัวข้อ 12.2 และ 13.2) — เก็บไว้เพื่อบันทึกลำดับความคิด ไม่ใช่เพื่ออ้างอิงตัวเลข

## 1. ภาพรวมของงาน

**เป้าหมาย**: จำแนกระดับความรุนแรงของกระดูกสันหลังยุบ (Genant grade 0–3) ของกระดูก
แต่ละปล้อง (T3–L5, รวม 15 ปล้อง) จากภาพ DXA

**โครงสร้างระบบ**: แบ่งเป็น 2 ขั้น

```
ภาพ DXA ทั้งภาพ
    → [Stage 1] หาตำแหน่งแต่ละปล้อง แล้วตัดออกมา (ใช้ mask จากงานของรุ่นพี่)
    → [Stage 2] จำแนกความรุนแรงของแต่ละปล้อง  ← งานหลักของโปรเจกต์นี้
```

Stage 1 ไม่ได้พัฒนาเอง — ใช้ mask ที่มีอยู่แล้วจาก special problem ของรุ่นพี่
(ใช้ชุดข้อมูล DXA เดียวกัน จากคณะแพทยศาสตร์ โรงพยาบาลรามาธิบดี) ตามที่อาจารย์
ที่ปรึกษาระบุว่าต้องการเพียง proof-of-concept ของส่วน segmentation

**ข้อสังเกตสำคัญ 3 ข้อ**

**1. การหักกระจุกตัวที่รอยต่อทรวงอก-เอว (thoracolumbar junction)** — ปล้อง T11,
T12, L1 มีสัดส่วนการหักสูงที่สุด (16.4%, 26.2%, 28.6%) รวมกันคิดเป็น **592 จาก
978 ปล้องที่หักทั้งหมด หรือ 60.5%** ทั้งที่เป็นเพียง 3 ใน 15 ปล้อง

ตรงกับความรู้ทางคลินิกที่ทราบกันดี — บริเวณนี้เป็นจุดเปลี่ยนระหว่างกระดูกสันหลัง
ช่วงอกที่ค่อนข้างแข็ง กับช่วงเอวที่เคลื่อนไหวได้มากกว่า จึงรับแรงกดสะสมมากที่สุด

**2. ปล้องบนสุดแทบไม่มีการหักเลย** — T3 และ T4 มีปล้องที่หักเพียง 2 และ 1 ปล้อง
(0.5% และ 0.2%) ซึ่งแทบไม่มีสัญญาณให้โมเดลเรียนรู้ในบริเวณนี้

**3. จำนวนปล้องต่อระดับไม่เท่ากัน** — T3 มีเพียง 384 ปล้อง และ T4 มี 648 ปล้อง
เทียบกับปล้องอื่นที่มีราว 820–830 ปล้อง เพราะปล้องบนสุดมักอยู่นอกขอบเขตภาพ DXA
(ถูกเข้ารหัสเป็น `99` และไม่มี mask)

**ผลกระทบต่อการตีความ**: การกระจายที่ไม่สม่ำเสมอนี้อธิบายว่าทำไมโมเดลจึงต้องรู้
ว่ากำลังดูปล้องไหน (ผ่าน level embedding) — ความน่าจะเป็นเบื้องต้นของการหักที่ L1
สูงกว่าที่ T4 ถึงเกือบ 150 เท่า และยังหมายความว่า**ตัวเลข recall รายปล้องในผล
การทดลองต้องอ่านควบคู่กับจำนวนตัวอย่างเสมอ** เพราะหลายปล้องมีตัวอย่างที่หัก
น้อยมากจนตัวเลขผันผวนสูง

## 3. การตั้งค่าที่ใช้ร่วมกันทุกการทดลอง

### 3.1 สถาปัตยกรรมโมเดล

```
รูป crop ปล้องเดียว → [backbone] → feature
ตำแหน่งปล้อง (T3–L5) → [level embedding 15×32] → เวกเตอร์
                              ↓ ต่อกัน
                        [head: Dropout + Linear] → Genant grade
```

**ทำไมต้องบอกตำแหน่งปล้องให้โมเดลด้วย**: กระดูกช่วงอกบางปล้องมีรูปทรงเอียงเล็กน้อย
ตามธรรมชาติ ซึ่งหน้าตาคล้ายการหักระดับเล็กน้อย การบอกว่ากำลังดูปล้องไหนช่วยให้
โมเดลแยกแยะ "ปกติของปล้องนั้น" ออกจาก "หักจริง" ได้ โดยยังใช้ backbone ตัวเดียว
ร่วมกันทุกปล้อง (ได้ประโยชน์จากการเรียนรู้ร่วมกัน ไม่ต้องแยกโมเดล 15 ตัว)

### 3.2 การเตรียมภาพ

ทำเท่าที่จำเป็นทางเทคนิคเท่านั้น **ไม่มี augmentation และไม่มี preprocessing ใดๆ**
(ตั้งใจให้เป็น baseline ที่ "เปลือย" ที่สุด เพื่อใช้เป็นจุดเทียบเมื่อเพิ่มเทคนิคทีหลัง)

1. ย่อภาพให้พอดีกรอบ โดยรักษาสัดส่วนเดิม (ไม่บีบ กันกระดูกผิดสัดส่วน) แล้วเติมขอบดำ
   ให้เป็นจัตุรัส — เรียกวิธีนี้ว่า `resize_mode="pad"` (ค่าเริ่มต้นของทุกการทดลอง
   ก่อนหน้าหัวข้อ 4.2 การทดลองที่ 6)
2. ทำภาพขาวดำให้เป็น 3 ช่องสี (backbone ต้องการ 3 ช่องเสมอ)
3. ปรับสเกลตัวเลขตามค่ามาตรฐานของ backbone ที่ใช้

ภายหลังเพิ่มตัวเลือก `resize_mode="stretch"` (ยืดภาพเต็มกรอบตรงๆ ไม่รักษาสัดส่วน
ไม่เติมขอบดำ) ตามที่อาจารย์ที่ปรึกษาเสนอให้ลอง — รายละเอียดในการทดลองที่ 6

### 3.3 การเทรน

| พารามิเตอร์ | ค่า |
|---|---|
| Loss | Focal Loss (γ = 2) + inverse-frequency class weight |
| Optimizer | AdamW, lr = 1e-4, weight decay = 1e-4 |
| Batch size | 64 (RAD-DINO ใช้ 32) |
| Epochs | 15 (early stopping, patience = 3) |
| Scheduler | CosineAnnealingLR |
| Seed | 42 (ทุกการทดลอง) |
| เกณฑ์เลือกโมเดล | **macro F1 บนชุด val** |

**ทำไมใช้ Focal Loss แทน loss มาตรฐาน**: ข้อมูลปกติมีถึง 92% ถ้าใช้ loss ธรรมดา
โมเดลจะพบว่า "ทายปกติทุกครั้ง" ก็ได้คะแนนดีแล้ว และไม่ยอมเรียนรู้ที่จะจับปล้องที่หัก

> **[อัปเดตภาคที่ 2 — ดูหัวข้อ 14.2]** เหตุผลข้างล่างยังถูก แต่ macro F1 บนชุด val
> ของงานนี้แกว่ง sd 2.29 pp ซึ่งกว้างกว่าเกณฑ์ 2 pp ที่ใช้ตัดสินว่า "เสมอ"
> เพิ่มตัวเลือก `train.select_metric` แล้ว

**ทำไมเลือกโมเดลด้วย macro F1 ไม่ใช่ accuracy**: ด้วยข้อมูลไม่สมดุลขนาดนี้
accuracy สูงได้โดยไม่มีประโยชน์ ส่วน macro F1 เฉลี่ยทุกคลาสเท่าๆ กัน คลาสไหนแย่
จะดึงคะแนนรวมลงทันที

### 3.4 การใช้ชุด test

ใช้ชุด test **ครั้งเดียวตอนจบ** ของแต่ละการทดลองเท่านั้น การตัดสินใจทุกอย่างระหว่าง
ทาง (เลือก epoch ที่ดีที่สุด, early stopping) ใช้ชุด val ล้วนๆ

### 3.5 กฎตัดสินใจ (ตั้งไว้ก่อนเห็นผล)

| ผลต่าง | การตีความ |
|---|---|
| มากกว่า 5 pp | น่าจะเป็นความต่างจริง |
| 2–5 pp | ยังสรุปไม่ได้ ต้องรันหลาย seed ยืนยัน |
| น้อยกว่า 2 pp | ถือว่าเสมอ |

ตั้งกฎนี้ไว้ก่อนเริ่มทดลอง เพื่อไม่ให้เผลอเข้าข้างผลที่อยากได้ภายหลัง

### 4.2 รายละเอียดแต่ละการทดลอง

#### การทดลองที่ 1 — EfficientNet-B0 + bbox crop (baseline)

จุดอ้างอิงของทุกการทดลอง ใช้ภาพที่ตัดแบบ bounding box ธรรมดา (มีพื้นหลังและขอบ
ปล้องข้างเคียงติดมาด้วย)

#### การทดลองที่ 2 — RAD-DINO + bbox crop

ทดสอบว่า backbone ที่ผ่านการ pretrain บนภาพ X-ray โดยเฉพาะ (RAD-DINO เป็น ViT
ที่ฝึกบนภาพ chest X-ray 883,000 ภาพ) จะดีกว่า backbone ที่ pretrain บนภาพทั่วไปไหม

**ผลที่ได้ให้คำตอบสองทาง**:
- macro F1 ต่ำกว่า baseline 6.1 pp (0.367 vs 0.428)
- แต่ AUC สูงกว่าเล็กน้อย (0.811 vs 0.797) และ **จับปล้องรุนแรงได้ดีกว่ามาก**
  (recall 0.771 vs 0.457)

**สาเหตุจากการวิเคราะห์ confusion matrix**: RAD-DINO ทายว่า "หัก" เกินจริงไปมาก
(ทายว่าเล็กน้อย 239 ครั้ง ทั้งที่ของจริงมี 46 ครั้ง) จึงจับ severe ได้ดีเพราะ
"ตื่นตัว" กับทุกอย่างที่ดูผิดปกติ แลกมาด้วย false positive จำนวนมากซึ่งฉุด
macro F1 ลง

**⚠️ ข้อจำกัดสำคัญ**: การเทียบนี้**ไม่เป็นธรรม** เพราะ RAD-DINO ถูกตั้งค่าให้
freeze backbone (เทรนเฉพาะ head) ขณะที่ EfficientNet-B0 fine-tune ทั้งโมเดล
เหตุผลคือข้อจำกัดของ VRAM 8GB และเวลา — รายละเอียดในหัวข้อ 6

#### การทดลองที่ 3 — EfficientNet-B0 + masked crop

เปลี่ยนจากภาพ bbox เป็นภาพที่ลบพื้นหลังออก (ทาสีดำทับทุกจุดที่ไม่ใช่ปล้องนั้น)

**ผลชัดเจนที่สุดของรอบนี้** — ดีขึ้นทั้งสองตัวชี้วัดหลัก:
- macro F1: 0.428 → 0.547 (**+11.9 pp**)
- AUC: 0.797 → 0.861 (**+6.4 pp**)

แต่เมื่อแยกดูราย grade พบว่า**ไม่ได้ดีขึ้นทุกด้าน**:

| grade | bbox | masked | ผล |
|---|---|---|---|
| ปกติ | 0.868 | 0.954 | ดีขึ้นมาก |
| **เล็กน้อย** | **0.261** | **0.196** | **แย่ลง** |
| ปานกลาง | 0.353 | 0.314 | แย่ลงเล็กน้อย |
| รุนแรง | 0.457 | 0.714 | ดีขึ้นมาก |

ตัวเลขรวมที่ดีขึ้นมาจากคลาสปกติ (ก้อนใหญ่สุด) และคลาสรุนแรง (สำคัญทางคลินิกสุด)
เป็นหลัก

**ตัดสินใจ**: ใช้ masked เป็นฐานของการทดลองที่เหลือ

#### การทดลองที่ 4 — เพิ่ม metadata (อายุ เพศ น้ำหนัก ส่วนสูง)

เพิ่มข้อมูลผู้ป่วยเข้าไปเป็น input เสริมควบคู่กับภาพ

**ผลอยู่ในโซนที่สรุปไม่ได้**: macro F1 +3.2 pp (0.547 → 0.579) ตกอยู่ในช่วง 2–5 pp
ตามกฎที่ตั้งไว้ ซึ่งแปลว่ายังแยกไม่ออกจากความผันผวนตามธรรมชาติ

**และมีสัญญาณที่น่ากังวล**:

| grade | ไม่มี metadata | มี metadata | ผล |
|---|---|---|---|
| **เล็กน้อย** | **0.196** | **0.130** | **แย่ลง** |
| ปานกลาง | 0.314 | 0.392 | ดีขึ้น |
| รุนแรง | 0.714 | 0.829 | ดีขึ้น |

**รูปแบบนี้อธิบายได้ด้วยเหตุผลเชิงโครงสร้าง**: metadata เป็นข้อมูล**ระดับผู้ป่วย**
แต่โจทย์เป็น**ระดับปล้อง** — ปล้องทั้ง 15 ปล้องของคนเดียวกันได้ metadata ชุดเดียว
กันหมด จึงบอกได้แค่ "ผู้ป่วยรายนี้เสี่ยงแค่ไหน" แต่บอกไม่ได้ว่า "ปล้องไหนหัก"
ผลคือช่วยที่ปลายสุด (severe ซึ่งมักพบในผู้ป่วยเสี่ยงสูง) แต่ไม่ช่วย — หรืออาจ
รบกวน — กลุ่มที่ต้องอาศัยการดูภาพจริงๆ (mild)

**ข้อควรระวังเพิ่มเติม**: เพศในชุดข้อมูลนี้มีหญิง 804 : ชาย 29 เกือบเป็นค่าคงที่
จึงแทบไม่ให้ข้อมูลอะไร และพบผู้ป่วย 1 รายที่กรอกน้ำหนัก-ส่วนสูงสลับกัน (154.5 กก.
สูง 54.5 ซม.) ซึ่งระบบตรวจจับและแทนด้วยค่ามัธยฐานโดยอัตโนมัติ

**สรุป**: ยังไม่นำมาใช้ — แต่ควรระบุว่า "ยังพิสูจน์ไม่ได้ว่าช่วย" ไม่ใช่
"ไม่ช่วย" ซึ่งต่างกันมากในเชิงวิชาการ

#### การทดลองที่ 5 — เปลี่ยนโจทย์เป็น binary

ยุบ grade 1, 2, 3 รวมเป็นคลาสเดียว ("เสียหาย") เหลือ 2 คลาส เพื่อลดปัญหาความ
ไม่สมดุล (จาก 40:1 เหลือ 11:1, ตัวอย่างกลุ่มน้อยเพิ่มจาก 270 เป็น 978 ปล้อง)

**ผลชัดเจนว่าช่วยจริง** — recall ราย grade (ซึ่งเทียบข้ามโจทย์ได้) ดีขึ้นทุกระดับ:

| grade | multiclass | binary | ผลต่าง |
|---|---|---|---|
| เล็กน้อย | 0.196 | 0.348 | **+15.2 pp** |
| ปานกลาง | 0.314 | 0.667 | **+35.3 pp** |
| รุนแรง | 0.714 | 1.000 | **+28.6 pp** (จับได้ครบทุกปล้อง) |

**โปรไฟล์การคัดกรอง** (จาก confusion matrix):
```
จับปล้องที่หักได้        85 จาก 132 ปล้อง  (64.4%)
สัญญาณเตือนผิดพลาด      41 จาก 1,548 ปล้องปกติ  (2.6%)
```

**แต่ mild ยังเป็นคอขวด**: จาก 47 ปล้องที่พลาดไป **30 ปล้อง (64%) เป็น mild**
ทั้งที่ยุบคลาสไปแล้ว

#### การทดลองที่ 6 — resize mode: pad vs stretch (ข้อเสนอของอาจารย์ที่ปรึกษา)

อาจารย์เสนอให้ลองยืดภาพเต็มกรอบตรงๆ (`stretch`) แทนการเติมขอบดำ (`pad`) เพราะ
Grad-CAM ในการทดลองที่ 3 พบว่าโมเดล masked บางเคสไปมองพื้นที่ดำว่างแทนตัวกระดูก
— `stretch` ตัดปัญหานี้ได้เพราะไม่มีพื้นที่ว่างเหลือเลย แต่แลกมาด้วยความเสี่ยงที่
กระดูกแต่ละปล้องจะโดนบิดสัดส่วนไม่เท่ากัน (ปล้องที่แบนจากการหักรุนแรงจะโดนยืด
แนวตั้งมากกว่าปล้องปกติ) ซึ่งอาจกระทบการวัดความสูงที่เป็นหลักการของ Genant grade
โดยตรง

ทดสอบทั้ง 2 crop variant (bbox และ masked) เทียบกับ baseline `pad` ของแต่ละแบบ:

| | bbox: pad → stretch | masked: pad → stretch |
|---|---|---|
| macro F1 | 0.428 → 0.481 (**+5.3 pp**) | 0.547 → 0.576 (+2.9 pp) |
| AUC | 0.797 → 0.771 (**−2.6 pp**) | 0.861 → 0.860 (ไม่เปลี่ยน) |
| recall ปกติ | 0.868 → 0.953 (ดีขึ้น) | 0.954 → 0.979 (ดีขึ้น) |
| recall เล็กน้อย | 0.261 → 0.130 (**แย่ลงมาก**) | 0.196 → 0.109 (แย่ลง) |
| recall ปานกลาง | 0.353 → 0.294 (แย่ลง) | 0.314 → 0.353 (ดีขึ้น) |
| recall รุนแรง | 0.457 → 0.543 (ดีขึ้น) | 0.714 → 0.800 (ดีขึ้น) |

**ผลไม่ได้ตอบง่ายๆ อย่างที่หวัง**:

- macro F1 ของ bbox ดีขึ้นเกินเกณฑ์ 5 pp (น่าจะจริง) แต่ของ masked ดีขึ้นแค่
  2.9 pp (อยู่ในโซนสรุปไม่ได้ตามกฎที่ตั้งไว้)
- **AUC กับ macro F1 ให้ทิศทางขัดกันในกรณี bbox** (macro F1 ดีขึ้น แต่ AUC แย่ลง)
  — สัญญาณว่า stretch อาจทำให้โมเดลมั่นใจผิดที่มากขึ้น แม้ทายถูกบ่อยขึ้นก็ตาม
- รูปแบบที่สอดคล้องกันทั้ง 2 variant: **mild แย่ลงเสมอ, severe ดีขึ้นเสมอ** —
  ตรงกับสมมติฐานว่า stretch ช่วยให้สัญญาณที่ชัดอยู่แล้ว (severe) ชัดขึ้นไปอีก
  แต่ไม่ได้ช่วยแยกแยะสัญญาณที่บางอยู่แล้ว (mild) เลย อาจถึงขั้นทำให้แย่ลง
- moderate ให้ผลกลับทิศกันระหว่าง bbox (แย่ลง) กับ masked (ดีขึ้น) — ยังไม่มี
  คำอธิบายที่ชัดเจนสำหรับความต่างนี้

**ข้อสังเกตทางเทคนิค**: การทดลอง masked+stretch เป็นรอบเดียวที่ไม่เกิด early
stopping เลย (`best_epoch=15` เต็มจำนวนรอบที่ตั้งไว้) ต่างจากทุกการทดลองอื่นที่
หยุดก่อนกำหนดเสมอ (epoch 4–9) — อาจแปลว่ายังไม่ถึงจุดอิ่มตัว ควรลองเพิ่ม epoch
ถ้าจะสรุปผลจริงจัง

**ยังไม่ได้ทำ Grad-CAM กับโมเดล stretch** — เป็นขั้นตอนสำคัญที่ต้องทำต่อ เพื่อ
ตรวจสอบว่าปัญหา "มองมุมดำ" ที่เจอใน masked+pad หายไปจริงตามที่คาดไว้หรือไม่ และ
เพื่อดูว่าการบิดสัดส่วนส่งผลต่อบริเวณที่โมเดลสนใจอย่างไร

#### การทดลองที่ 7 — EfficientNet-B4 (224px, fine-tune เต็ม)

ทดสอบ backbone ที่ใหญ่กว่า B0 (~19M พารามิเตอร์ เทียบ B0 ที่ ~4M) โดยตั้งใจเทียบ
กับ RAD-DINO แบบที่ควบคุมตัวแปรให้เท่ากันมากที่สุด (fine-tune เต็มทั้งคู่)

**หมายเหตุสำคัญเรื่อง img_size**: เดิมวางแผนให้ทั้ง B4 และ RAD-DINO ใช้ 380px
(สเปกทางการของ B4) เพื่อให้ทั้งคู่ใช้ขนาดภาพเท่ากันเป๊ะ แต่ระหว่างรันจริงบน RTX
4060 Ti (VRAM 8GB) พบว่าใช้เวลานานเกินกว่าที่มี (GPU ทำงาน 100% ต่อเนื่องนาน
20+ นาทียังไม่จบ 1 epoch) จึงตัดสินใจ**ลด img_size กลับเป็น 224px** เพื่อให้ทัน
เวลา — ผลที่ได้ในตารางนี้จึงมาจาก 224px ไม่ใช่ 380px ตามแผนเดิม

เทียบกับ EfficientNet-B0 + masked (baseline, macro F1 0.547):

| | B0 (baseline) | B4 (224px) | ผลต่าง |
|---|---|---|---|
| macro F1 | 0.547 | 0.553 | +0.6 pp (ถือว่าเสมอ) |
| AUC | 0.861 | 0.891 | **+3.0 pp** |
| recall ปกติ | 0.954 | 0.915 | −3.9 pp |
| recall เล็กน้อย | 0.196 | 0.239 | +4.3 pp |
| recall ปานกลาง | 0.314 | **0.588** | **+27.4 pp** |
| recall รุนแรง | 0.714 | 0.629 | −8.5 pp |

**macro F1 แทบไม่ต่างกัน แต่โปรไฟล์ข้อผิดพลาดต่างกันมาก** — B4 แลก recall ของ
severe ที่ลดลงเพื่อแลกกับ moderate ที่ดีขึ้นมหาศาล ไม่ใช่กรณีที่ backbone หนึ่ง
"ดีกว่า" อีกอันทุกด้าน แต่เป็นการ trade-off ที่ต่างจุดกัน

**ยังตอบคำถามหลัก (B4 vs RAD-DINO แบบแฟร์) ไม่ได้** — เพราะ RAD-DINO แบบ
fine-tune เต็ม (ที่ตั้งใจเทียบคู่กับ B4 นี้) **ยังไม่ได้รัน** ตัวเลข RAD-DINO ที่มี
อยู่ในตารางสรุป (แถวที่ 2) เป็นแบบ frozen backbone บน bbox variant คนละเงื่อนไข
ทั้งการ freeze และ crop variant เทียบกับ B4 แถวนี้ตรงๆ ไม่ได้เลย

#### การทดลองที่ 8 — ยุบเป็น 3 คลาส (ปกติ / เสียหายปานกลาง / เสียหายมาก)

ทดลองยุบ grade ต่างจาก binary — แทนที่จะรวม grade 1-3 เป็นกลุ่มเดียว ("เสียหาย")
ทดลองนี้**แยก severe ออกมาต่างหาก** และรวมแค่ mild กับ moderate เข้าด้วยกันเป็น
"เสียหายปานกลาง" (grade 0→ปกติ, grade 1,2→เสียหายปานกลาง, grade 3→เสียหายมาก)
ทดสอบทั้งบน `resize_mode: pad` (8a) และ `stretch` (8b) เพื่อดูว่าข้อสรุปเรื่อง
resize จากการทดลองที่ 6 ยังเป็นจริงไหมเมื่อเปลี่ยนโจทย์เป็นยุบคลาส — **นี่คือ
2 การทดลองคนละ config กัน ไม่ใช่การรันซ้ำด้วย config เดียวกัน**

| | 8a: pad | 8b: stretch | ผลต่าง |
|---|---|---|---|
| macro F1 | 0.735 | 0.729 | −0.6 pp (ถือว่าเสมอ) |
| AUC | 0.917 | 0.919 | +0.2 pp (ถือว่าเสมอ) |
| recall ปกติ | 0.970 | 0.966 | −0.4 pp |
| recall เล็กน้อย | 0.304 | **0.391** | **+8.7 pp** |
| recall ปานกลาง | 0.627 | 0.627 | เท่ากันเป๊ะ |
| recall รุนแรง | 0.714 | 0.714 | เท่ากันเป๊ะ |

**ข้อสังเกตที่มีค่า**: recall ของ moderate และ severe **เท่ากันเป๊ะทั้ง 2 config**
(แถวสอดคล้องกันทุกตัวเลขใน confusion matrix) — resize mode ไม่ส่งผลต่อการจับกลุ่ม
เหล่านี้เลยในโจทย์ 3 คลาส ในขณะที่ recall ของ mild เปลี่ยนชัดเจน (+8.7 pp) แปลว่า
ความผันผวนจาก resize mode กระจุกอยู่ที่**รอยต่อ normal-mild** เป็นหลัก ตรงกับที่
สรุปไว้แล้วในหัวข้อ 5.3 ว่าเส้นแบ่งนี้บางที่สุด — หลักฐานอิสระอีกชุดที่ชี้ไปทางเดียวกัน

**จุดที่น่าสนใจที่สุด — ทิศทางกลับกันกับโจทย์ 4 คลาส**: ในการทดลองที่ 6 (4 คลาส)
stretch ทำให้ recall ของ mild **แย่ลง** ทั้ง 2 crop variant (bbox: −13.1 pp,
masked: −8.7 pp) แต่พอยุบ mild เข้ากับ moderate ในโจทย์นี้ stretch กลับทำให้
recall ของกลุ่มที่รวมกันนั้น **ดีขึ้น** (+8.7 pp) คำอธิบายที่เป็นไปได้: stretch
อาจทำให้แยก "mild ออกจาก normal" ยากขึ้น (สัญญาณบางอยู่แล้วยิ่งเพี้ยน) แต่การ
แยก "กลุ่มที่เสียหายแบบใดก็ได้ ออกจาก normal" (ซึ่งเป็นสิ่งที่โจทย์นี้ถามจริงๆ
หลังยุบคลาส) ทำได้ง่ายขึ้น เพราะไม่ต้องแยกแยะความละเอียดอ่อนระหว่าง mild กับ
moderate อีกต่อไป — เป็นสมมติฐานที่ยังไม่ได้ตรวจสอบเพิ่มเติม

**เทียบกับ multiclass/binary**: recall ของ "เสียหายปานกลาง" (0.627, รวม mild+
moderate) อยู่**ระหว่างกลาง**ของ multiclass mild (0.196) และ multiclass moderate
(0.314) ทั้งคู่ต่ำกว่า — สมเหตุสมผลเพราะเป็นผลจากการรวม 2 กลุ่มที่มีพฤติกรรม
ต่างกัน severe recall (0.714) เท่ากับที่ multiclass ได้พอดีทั้ง 8a และ 8b (ไม่ต่าง
จากที่คาด เพราะ 3class ไม่ได้เปลี่ยนอะไรกับตัว severe เลย ยังคงแยกเดี่ยวเหมือนเดิม)

**ยังไม่ได้ทำ Grad-CAM กับการทดลองนี้ทั้ง 8a และ 8b**

### 4.3 การตรวจสอบด้วย Grad-CAM

รัน Grad-CAM บนโมเดลทั้ง bbox และ masked (การทดลองที่ 1 และ 3) เพื่อดูว่าโมเดลใช้
บริเวณไหนของภาพในการตัดสินใจ — **ยังไม่ได้ทำกับการทดลองที่ 6, 7, 8** (stretch,
B4, 3class) เป็นงานที่ต้องทำต่อ โดยเฉพาะการทดลองที่ 6 (stretch) ที่ควรตรวจสอบ
ว่าแก้ปัญหาที่พบด้านล่างได้จริงหรือไม่

**ผลที่พบ — ไม่เป็นผลดีกับ masked**:

- ในโมเดล **bbox** สีร้อน (บริเวณที่มีอิทธิพลสูง) อยู่**บนเนื้อกระดูก**เกือบทุกภาพ
  (9 จาก 12 ภาพ)
- ในโมเดล **masked** พบหลายกรณีที่สีร้อนอยู่ใน**มุมภาพที่เป็นพื้นดำล้วน ไกลจาก
  กระดูก** โดยเฉพาะในเคสที่ทายถูก เช่น ปล้อง T11 ที่ทาย severe ถูก แต่ตัวกระดูก
  แทบไม่มีสีร้อนเลย

**ข้อสังเกตที่ต้องให้ความเป็นธรรม**: บางภาพของ masked มีสีร้อนเป็นแถบตั้งที่
**ขอบซ้าย-ขวาของกระดูก** ซึ่ง**อาจไม่ใช่ข้อผิดพลาด** เพราะการวัด Genant grade
ใช้สัดส่วนความสูงที่ขอบหน้า-กลาง-หลังของกระดูก จุดที่ต้องวัดคือขอบพอดี ต้องแยก
ให้ออกระหว่าง "สีร้อนที่ขอบกระดูก" (มีเหตุผล) กับ "สีร้อนที่มุมภาพว่างๆ"
(ไม่มีความหมาย)

**สรุป**: ข้อได้เปรียบเชิงตัวเลขของ masked **ยังอธิบายด้วย "โมเดลเข้าใจกระดูก
ดีขึ้น" ไม่ได้เต็มปาก** — ต้องบันทึกเป็นข้อจำกัด

### 4.4 การทดลองที่ยกเลิกกลางคัน

**ConvNeXt-Tiny + bbox** — ยกเลิกเพราะใช้เวลานานเกินกว่าเวลาที่มี (โมเดลมี
พารามิเตอร์ 27.8 ล้าน เทียบกับ EfficientNet-B0 ที่ 4 ล้าน) เดิมตั้งใจรันเพื่อ
เทียบกับ backbone ที่รุ่นพี่ใช้ (ได้ AUC 95.13% ในงานของเขา)

## 5. ข้อค้นพบหลัก

### 5.1 Masked crop ให้ผลดีกว่า bbox อย่างชัดเจน

ดีขึ้น 11.9 pp ซึ่งเกินเกณฑ์ 5 pp ที่ตั้งไว้ **แต่ Grad-CAM ชี้ว่าส่วนหนึ่งอาจ
มาจากสัญญาณที่ไม่เกี่ยวข้องทางคลินิก** — ควรรายงานทั้งสองด้าน

### 5.2 การยุบคลาสเป็น binary ช่วยการตรวจจับได้จริงทุกระดับ

โดยเฉพาะคลาสรุนแรงที่จับได้ครบ 100% เหมาะกับการใช้เป็นเครื่องมือคัดกรองเบื้องต้น
ในทางคลินิก

### 5.3 คลาส "เล็กน้อย" (mild) เป็นข้อจำกัดเชิงโครงสร้าง ไม่ใช่ปัญหาการออกแบบ

หลักฐานจากทุกทิศทางชี้ไปทางเดียวกัน:

| วิธีที่ลอง | ผลกับ mild |
|---|---|
| เปลี่ยนแบบ crop (bbox → masked) | แย่ลง (0.261 → 0.196) |
| เพิ่ม metadata | แย่ลง (0.196 → 0.130) |
| ยุบคลาสเป็น binary | ดีขึ้นแต่ยังต่ำ (0.196 → 0.348) |
| เปลี่ยน backbone เป็น RAD-DINO | ดีขึ้นเล็กน้อย (0.261 → 0.283) |

> **[แก้แล้วในภาคที่ 2 — ดูหัวข้อ 14.1]** ข้อสรุปด้านล่างอิงจากหลักฐาน 4 ทางที่
> ไม่มีทางไหนเป็น regularization เลย เมื่อทดสอบ augmentation แล้วพบว่า recall ของ
> mild ขึ้นจาก 0.217 เป็น 0.630 ได้ด้วยเทคนิคการเทรนล้วนๆ ไม่ได้เพิ่มข้อมูลเลย

**ข้อสรุป**: ปัญหาน่าจะมาจากตัวอย่างที่น้อยเกินไป (ชุด train มี mild เพียง 224
ปล้อง) ประกอบกับความยากทางคลินิกเองที่ mild แยกจาก normal ได้ยากแม้แต่สำหรับ
ผู้เชี่ยวชาญ — **ไม่น่าแก้ได้ด้วยเทคนิคการเทรน ต้องการข้อมูลเพิ่ม**

### 5.4 Resize mode (pad vs stretch) ส่งผลต่างกันขึ้นกับว่า mild ถูกแยกเดี่ยวหรือถูกยุบรวม

ในโจทย์ 4 คลาส (mild แยกเดี่ยว) stretch ทำให้ recall ของ mild **แย่ลงเสมอ**
ทั้ง bbox (−13.1 pp) และ masked (−8.7 pp) — สอดคล้องกับสมมติฐานว่าการบิดสัดส่วน
กระทบสัญญาณที่บางอยู่แล้วของ mild โดยตรง แต่พอยุบ mild เข้ากับ moderate ในโจทย์
3class stretch กลับทำให้ recall ของกลุ่มที่รวมกันนั้น **ดีขึ้น** (+8.7 pp) — บอกว่า
stretch อาจช่วยแยก "เสียหายแบบใดก็ได้ ออกจาก normal" (โจทย์หยาบ) ได้ดีขึ้น แม้จะ
ทำให้แยกความละเอียดอ่อนระหว่าง mild กับ moderate (โจทย์ละเอียด) แย่ลงก็ตาม —
**คำตอบว่า pad หรือ stretch ดีกว่าจึงขึ้นอยู่กับว่าจะใช้ระบบนี้ทำอะไร** (คัดกรอง
หยาบๆ vs ให้เกรดละเอียด) ไม่ใช่คำตอบเดียวที่ใช้ได้ทุกกรณี — ยังไม่ได้ตรวจสอบ
ด้วย Grad-CAM ว่าสมมติฐานนี้ถูกจริงหรือไม่

### 5.5 โจทย์ 3class เป็นจุดกึ่งกลางที่คุ้มค่าระหว่าง multiclass กับ binary

3class ให้ recall ของกลุ่ม "เสียหายปานกลาง" (รวม mild+moderate, 0.627) ที่ดีขึ้น
มากจาก multiclass เดิม (mild 0.196, moderate 0.314) เกือบเท่า binary (mild 0.348,
moderate 0.667) **โดยที่ยังแยก severe ออกมาต่างหากได้** (recall 0.714 เท่ากับ
multiclass) ซึ่ง binary ทำไม่ได้ (severe recall 1.000 ของ binary สูงเทียม เพราะ
รวม severe เข้ากับกลุ่มเสียหายทั้งหมดจนกลายเป็นงานที่ง่ายเกินไป) — 3class จึงเป็น
ทางเลือกที่รักษาความสามารถแยก "รุนแรงแค่ไหน" ไว้บางส่วน ในขณะที่ยังได้ประโยชน์
จากการยุบคลาสส่วนใหญ่ของปัญหาความไม่สมดุล

## 6. ข้อจำกัดที่ต้องพิจารณา

### 6.1 ทุกผลมาจาก seed เดียว — ยังยืนยันความน่าเชื่อถือไม่ได้

ชุด val มีคลาสรุนแรงเพียง 40 ปล้อง และคลาสเล็กน้อย 47 ปล้อง การทายพลาดเพิ่ม
เพียง 2–3 ปล้องทำให้ macro F1 เปลี่ยนได้ 2–3 pp

**ผลกระทบ**: ผลของ metadata (+3.2 pp) **อยู่ในช่วงที่แยกไม่ออกจากความผันผวน**
ยังสรุปไม่ได้ว่าช่วยจริงหรือไม่

**สิ่งที่ควรทำ**: รันซ้ำด้วย seed อื่นอย่างน้อย 3 ค่า แล้วรายงานเป็นค่าเฉลี่ย ±
ส่วนเบี่ยงเบนมาตรฐาน

### 6.2 การเทียบ RAD-DINO กับ EfficientNet-B0 ไม่เป็นธรรม

| | EfficientNet-B0 | RAD-DINO |
|---|---|---|
| การเทรน | fine-tune ทั้งโมเดล (4M พารามิเตอร์) | freeze backbone เทรนแค่ head |
| ขนาดภาพ | 224×224 | 224×224 (ทางการคือ 518×518) |
| learning rate | 1e-4 | 1e-3 |

เหตุผลของการตั้งค่าเหล่านี้คือข้อจำกัดของ VRAM 8GB (ที่ 518×518 ViT ต้องประมวลผล
1,369 ชิ้นส่วนภาพ กลไก attention กินหน่วยความจำแบบกำลังสอง) และเวลาที่มีจำกัด

**ผลกระทบ**: หาก RAD-DINO ได้ผลด้อยกว่า **อาจเป็นเพราะการ freeze ไม่ใช่เพราะ
pretrained feature ไม่ดี** — ยังสรุปไม่ได้ว่า domain-specific pretraining ไม่ช่วย

### 6.3 ยังไม่ได้ปรับ learning rate แยกตาม backbone

ใช้ lr = 1e-4 เหมือนกันทุก backbone (ยกเว้น RAD-DINO) ซึ่ง ViT มักต้องการ lr ที่
ต่ำกว่า CNN — backbone ที่ได้ผลด้อยกว่าอาจเพียงแค่ lr ไม่เหมาะสม

### 6.4 ใช้วิธี greedy sequential ablation ซึ่งสมมติว่าการตัดสินใจไม่เกี่ยวข้องกัน

เลือก backbone ตอนที่ยังไม่มี augmentation → เลือกแบบ crop → เพิ่ม metadata
ตามลำดับ วิธีนี้สมมติว่า "backbone ที่ดีที่สุดตอนไม่มี augmentation จะยังดีที่สุด
ตอนมี augmentation" ซึ่งไม่จริงเสมอไป

เป็นข้อจำกัดที่ยอมรับได้ (การทดลองทุกคู่ผสมมีต้นทุนสูงเกินไป) แต่ควรระบุไว้

### 6.5 ตัวเลข macro F1 ของโจทย์ binary เทียบกับ multiclass โดยตรงไม่ได้

โจทย์ binary เฉลี่ยเพียง 2 คลาส และมีคลาส "ปกติ" ที่ง่ายมากอยู่ด้วย ทำให้ตัวเลข
สูงขึ้นเป็นธรรมดา **ต้องเทียบด้วย recall ราย grade เท่านั้น**

### 6.6 ยังไม่ได้ทดสอบ augmentation และ image preprocessing

> **[ตอบแล้วในภาคที่ 2 — ดูหัวข้อ 12 และ 14.3]** augmentation ได้ผลชัดเจน
> (AUC +8.0 pp, mild +32.6 pp) ส่วน preprocessing แบบปรับคอนทราสต์ไม่ได้ผล
> แต่การลบ artifact ลายเส้น (destriping) ได้ผล (mild +8.7 pp เพิ่มเติม)

การทดลองทั้งหมดใช้ภาพดิบที่ผ่านเพียงการปรับขนาดและสเกลตัวเลข — ยังไม่ทราบว่า
เทคนิคเหล่านี้จะช่วยได้แค่ไหน โดยเฉพาะกับปัญหาคลาส mild

### 6.7 ข้อจำกัดของการอ่าน Grad-CAM

1. heatmap คำนวณจากตารางความละเอียด 7×7 แล้วขยายเป็น 224×224 — สีจึงเลอะออกนอก
   ขอบเขตจริงได้ง่าย
2. ดูเพียง 3 ภาพต่อคลาส ตัวอย่างน้อยเกินกว่าจะสรุปเป็นกฎ
3. Grad-CAM บอกว่า "ตรงไหนมีอิทธิพล" ไม่ได้บอกว่า "โมเดลคิดอะไร" — เป็นเครื่องมือ
   ชี้เบาะแส ไม่ใช่หลักฐานตัดสิน

### 6.8 Grad-CAM ใช้กับ RAD-DINO ไม่ได้

RAD-DINO เป็น Vision Transformer ซึ่งไม่มีชั้น convolution ให้จับ heatmap โดยตรง
ต้องใช้เทคนิคคนละแบบ (attention rollout) ซึ่งยังไม่ได้ทำ

## 9. จุดเริ่มต้นของรอบที่ 2

### 9.1 สิ่งที่กระตุ้นให้ทำ

หัวข้อ 6.6 ของภาคที่ 1 ระบุไว้เองว่า **ยังไม่เคยทดสอบ augmentation และ image
preprocessing เลย** — การทดลองทั้งหมดใช้ภาพดิบที่ผ่านเพียงการปรับขนาดและสเกลตัวเลข
รอบนี้จึงเริ่มจากการเติมช่องว่างนั้น

### 9.2 สิ่งที่ค้นพบระหว่างทางและเปลี่ยนทิศทางของงาน

ระหว่างรัน baseline ที่ 50 epoch เพื่อเป็นจุดอ้างอิง พบว่า **โมเดล overfit อย่าง
รุนแรงกว่าที่เคยเข้าใจ**:

| epoch | train_loss | val_loss | val_F1 | val_AUC |
|---|---|---|---|---|
| 1 | 0.5277 | 0.401 | 0.4299 | 0.8779 |
| 2 | 0.2751 | 0.422 | 0.5214 | **0.8846** |
| 5 | 0.0343 | 0.703 | 0.5623 | 0.8541 |
| 15 | 0.0037 | 1.107 | 0.5745 | 0.8294 |
| 30 | 0.0001 | 1.317 | 0.5760 | 0.8417 |
| 44 (best F1) | 0.0001 | 1.366 | 0.5922 | 0.8360 |

**val_AUC ดีที่สุดตั้งแต่ epoch 2 แล้วลดลง 4.2 pp ตลอดทาง** ขณะที่ train_loss ลงถึง
0.0001 (จำภาพครบทั้ง 8,409 ใบ) — การเรียนรู้ที่มีประโยชน์จบตั้งแต่ epoch 2-4
ที่เหลืออีก 40 กว่า epoch คือการทำลายโมเดลอย่างช้าๆ

ผลบนชุด test ยืนยัน: 50ep/patience 15 ได้ macro F1 **0.530** และ recall ของ mild
เพียง **0.087** ซึ่ง**แย่กว่า**การทดลองที่ 3 เดิมที่ใช้ 15ep/patience 3 (0.547 และ
0.196) — การเทรนนานขึ้นไม่ได้ช่วย แต่กัดกินคลาสที่เปราะที่สุดก่อน

**จึงกลับมาใช้ 15 epoch / patience 3 ตามภาคที่ 1** ซึ่งได้ประโยชน์สองทาง: ผลดีกว่า
และเทียบกับตารางเดิมได้โดยตรง

## 10. โครงสร้างที่เพิ่มเข้ามาในโค้ด

ทุกส่วนออกแบบให้ **ปิดอยู่โดยค่าเริ่มต้น** — config เก่าทั้งหมดรันซ้ำได้ผลเดิมเป๊ะ
โดยไม่ต้องแก้แม้แต่บรรทัดเดียว และมีการทดสอบยืนยัน (null test) ทุกส่วน

### 10.1 กติกาพื้นหลัง 3 ข้อ — รากฐานของทุกอย่างที่ตามมา

crop แบบ `xray_masked` มีพื้นหลังเป็น 0 สนิทกินพื้นที่ **23%** ของกรอบ ซึ่งพัง
การคำนวณสถิติได้ทุกรูปแบบ (histogram มีแท่งยักษ์ที่ 0, percentile เลื่อน,
ค่าเฉลี่ยต่ำเกินจริง) ทุกฟังก์ชันแต่งภาพในรอบนี้จึงยึดกติกาเดียวกัน:

1. **คิดสถิติจากพิกเซลกระดูกเท่านั้น** (ค่ามากกว่า 0)
2. **ทาพื้นหลังกลับเป็น 0 เสมอหลังแต่งภาพ**
3. **พิกเซลกระดูกห้ามมีค่า 0** (บีบไปอยู่ที่ 1-255)

ข้อ 3 สำคัญที่สุดและพลาดง่ายที่สุด — ถ้าปล่อยให้พิกเซลกระดูกที่มืดที่สุดกลายเป็น 0
ฟังก์ชันตัวถัดไปในสายจะเข้าใจผิดว่าเป็นพื้นหลัง ทำให้รูปทรงกระดูกแหว่ง

กติกานี้ยังให้ผลพลอยได้ที่สำคัญ: **กู้ mask กลับมาได้จากเงื่อนไข `img > 0` โดยไม่ต้อง
re-crop** (ตรวจแล้วว่าในภาพ bbox ที่ไม่มีการทา mask มีพิกเซลค่า 0 เพียง 0.0005%)

### 10.2 ปลั๊ก preprocess (`data.preprocess`)

จุดเสียบสำหรับฟังก์ชันแต่งภาพแบบ **คงที่ ใช้กับทั้ง train/val/test** — เป็นส่วนหนึ่ง
ของ "วิธีอ่านภาพ" ไม่ใช่การเพิ่มความหลากหลาย

ฟังก์ชันที่เขียน: `normalize`, `clahe`, `normalize_clahe`, `destripe`,
`destripe_clahe`, `unsharp`, `flatten`, `destripe_unsharp`, `destripe_flatten`

### 10.3 ปลั๊ก augment (`data.augment`)

จุดเสียบแยกต่างหากสำหรับการดัดแปลงแบบ **สุ่ม ทำเฉพาะชุด train**

ควบคุมด้วยการ "ไม่ส่ง `augment_fn` ให้ dataset ของ val/test" ที่ฝั่ง `train.py`
แทนการมี flag ในคลาส เพราะ flag เผลอตั้งผิดได้ง่ายกว่า — ถ้าเผลอ augment ชุดวัดผล
ตัวเลขที่รายงานจะใช้ไม่ได้ทันที

ตำแหน่งในท่อ: `โหลดภาพ → preprocess → resize/pad → augment → ประกอบช่องสี → normalize`

augment อยู่ **หลัง** resize โดยตั้งใจ เพราะ crop ตัดชิดตัวกระดูก ถ้าหมุนก่อน pad
มุมกระดูกจะถูกตัดหาย แต่หลัง pad แล้วมีพื้นที่ดำรองรับ

### 10.4 ฟีเจอร์เรขาคณิตระดับปล้อง (`model.use_geometry`)

6 ฟีเจอร์อ่านจาก `manifest.csv` ที่ `crop.py` เขียนไว้แล้ว ไม่ต้อง re-crop:
`ar` (สูง/กว้าง), `fill` (พื้นที่กระดูก/พื้นที่กรอบ), `log_area`,
`h_rel`/`w_rel`/`ar_rel` (เทียบกับค่ามัธยฐานของปล้องอื่นในตัวคนไข้เอง)

แยกเป็นสายอิสระจาก metadata ในโมเดล เพื่อให้เปิด/ปิดแยกกันได้และไม่กระทบผลเดิม

### 10.5 สูตรช่องสี (`data.channels`)

เดิมโค้ดก๊อปช่องขาวดำ 3 ครั้ง ทำให้ 2 ใน 3 ช่องไม่ให้ข้อมูลใหม่เลย
เพิ่มตัวเลือก: `gray3` (เดิม), `gray_clahe_mask`, `gray_clahe_gray`, `gray_gray_mask`

### 10.6 เกณฑ์เลือกโมเดล (`train.select_metric`)

รับ `f1` (ค่าเริ่มต้น = เดิม), `auc`, `f1_auc` (เฉลี่ยสองตัว)
ใช้ทั้งการเลือก `best.pt` และการตัดสินใจ early stopping

### 10.7 การบันทึกผล

### 11.1 รูปทรงของ bbox สัมพันธ์กับ grade อย่างชัดเจน

`ar` = 0.712 — เทียบกับทั้งโมเดล CNN ที่ได้ 0.861

ตามธรรมชาติของกระดูกปกติ

`w_rel` เป็นฟีเจอร์เดียวที่แยก mild ได้พอใช้ (0.704) และสม่ำเสมอทุกระดับ

### 12.2 กลุ่ม augmentation (R1, R2)

> ⚠️ **ตารางข้อห้ามด้านล่างนี้ถูกพิสูจน์แล้วว่าผิด — ดูหัวข้อ 21 และ 26.1**
> flip / scale / elastic ที่ระบุว่า "ห้าม" ให้ผลดีกว่าชุดที่ปฏิบัติตามข้อห้าม
> เก็บข้อความเดิมไว้เพื่อบันทึกว่าตอนนั้นคิดอย่างไรและทำไมถึงคิดผิด

**การเลือก transform** — โจทย์นี้ใช้สูตร augmentation มาตรฐานไม่ได้ เพราะเกณฑ์
Genant นิยาม grade ด้วย **รูปทรง** โดยตรง ต่างจากงาน classification ทั่วไปที่
label ไม่ขึ้นกับรูปทรง

| transform | ตัดสิน | เหตุผล |
|---|---|---|
| flip แนวนอน | ❌ ห้าม | สลับด้านหน้า-หลัง anterior wedge (พบบ่อย) กลายเป็น posterior wedge (พบน้อยมาก) แต่ label ไม่เปลี่ยน = สอนว่าทิศทางไม่สำคัญ |
| flip แนวตั้ง | ❌ ห้าม | สลับ endplate บน-ล่าง ด้วยเหตุผลเดียวกัน |
| scale / zoom | ❌ ห้าม | ทำลาย `ar` และขนาดสัมบูรณ์ ซึ่งเป็นสัญญาณที่วัดได้ว่าแรงที่สุด |
| elastic / grid distort | ❌ ห้าม | บิดรูปทรง = บิด label |
| brightness / contrast / gamma / noise | ✅ ใช้ได้ | รบกวนความเข้ม ไม่แตะรูปทรง |
| หมุน ±7-10° + เลื่อน ±5-7% | ⚠️ ใช้ได้แบบจำกัด | ต้องเติมขอบด้วย 0 + ทา mask ซ้ำ + ใช้กับ `pad` เท่านั้น |

**การตั้งความแรงอิงจากข้อมูลจริง** ไม่ได้เดา — หลักการคือภาพที่ augment แล้วต้องยัง
"เป็นไปได้จริง" สำหรับเครื่องนี้ ถ้าแรงเกินความผันผวนตามธรรมชาติ เท่ากับสอนให้โมเดล
ทนต่อสิ่งที่ไม่มีวันเกิด

| ชุด | sd ความสว่างที่สร้างได้ | เทียบธรรมชาติ (37.7) |
|---|---|---|
| `intensity` | 11.5 | 30% |
| `standard` | 11.9 | 32% |
| `strong` | 23.6 | 63% |

**ผลการวินิจฉัย** — วัด `train_loss` ที่ epoch 15 ซึ่งบอกตรงๆ ว่าโมเดลจำภาพได้แค่ไหน:

| | train_loss @ ep15 | เทียบ baseline |
|---|---|---|
| ไม่มี augment | 0.0037 | — |
| intensity | 0.0174 | 4.7 เท่า |
| standard | 0.0665 | 18 เท่า |
| **strong** | **0.1217** | **33 เท่า** |

ไล่ระดับสวยงามตามความแรง และ `strong` ที่ epoch 15 ยังไม่ถึงจุดอิ่มตัวด้วยซ้ำ

**บั๊กที่เจอจากการดูภาพ (ตัวเลขไม่ฟ้อง)**: `strong` เวอร์ชันแรกทำให้ปล้องที่สว่าง
อยู่แล้วขาวจนหมดรายละเอียด เพราะ brightness +35% ไปชนเพดาน 255 แล้วถูก clip ทิ้ง
= ทำลายข้อมูล ไม่ใช่เพิ่มความหลากหลาย

แก้โดยให้แต่ละภาพคำนวณ "พื้นที่ว่างที่เหลือจริง" ของตัวเอง (จาก percentile 1 และ 99)
แล้วบีบการเลื่อนให้อยู่ในนั้น ผลคือพิกเซลอิ่มตัวเหลือ **0.11% ซึ่งต่ำกว่าภาพต้นฉบับ
เอง (0.37%)** ในขณะที่ความแรงเพิ่มขึ้นจาก sd 21.6 เป็น 23.6

### 12.3 กลุ่ม preprocessing บนฐาน augmentation (R3, R4)

ทั้ง `normalize` และ `clahe` อยู่ในโซน "เสมอ" เทียบกับ R2 ทั้งคู่ (−0.8 และ +1.0 pp)

**แต่ไม่ใช่ "ไม่มีผล" — เป็น "ผลย้ายที่"**: CLAHE ดัน moderate ขึ้น (0.392 → 0.471)
แลกกับ mild ที่ลดลง (0.543 → 0.478) ส่วน normalize ดัน severe ขึ้นสูงสุดในกลุ่ม
(0.829) แลกกับ mild เช่นกัน

| severe | 0.714 | 0.657 | −5.7 |
| normal | 0.915 | 0.968 | +5.3 |

**macro F1 ดีขึ้นแต่ AUC แย่ลง และ mild ร่วงครึ่งหนึ่ง** — โมเดลไปเชื่อฟีเจอร์รูปทรง
ที่บอกว่า "นี่ปกติ" แล้วกลบหลักฐานจากภาพทิ้ง ผลคือ normal ขึ้นเป็น 0.968 (สูงสุดใน
ทุกการทดลอง) ซึ่งดันค่ารวมขึ้นตาม

**เป็นการดันตัวเลขรวมด้วยการยอมแพ้กับคลาสที่ยากที่สุด** อธิบายได้ตรงกับหัวข้อ 11.1:
รูปทรงแยก mild จาก normal ไม่ได้ (AUC 0.512-0.603)

ถ้าจะใช้ geometry ต่อ ควรเหลือแค่ `w_rel` ซึ่งเป็นตัวเดียวที่แยก mild ได้ (0.704)
แทนที่จะยัดทั้ง 6 ตัว

### 12.5 สูตรช่องสี (R10, R11, R12)

**สมมติฐาน**: R2 (ภาพดิบ) เก่ง mild ส่วน R4 (CLAHE) เก่ง moderate — ถ้าใส่ทั้งคู่
คนละช่อง โมเดลน่าจะได้ทั้งสองอย่างโดยไม่เพิ่มพารามิเตอร์แม้แต่ตัวเดียว

**ผลไม่เป็นไปตามนั้น** — R11 ได้ mild เพียง 0.326 ซึ่งแย่กว่าทั้งสองตัวที่เอามารวม

**AUC ไม่ขยับเลยทั้ง 3 สูตร** (0.941 → 0.939 / 0.934 / 0.894) แปลว่าช่องที่เพิ่ม
เข้าไปไม่ได้เพิ่มข้อมูลที่แยกแยะได้จริง แค่ย้ายจุดตัดสินใจ

**คำอธิบายบางส่วน**: ภาพ pipeline ที่บันทึกไว้แสดงให้เห็นว่าช่อง CLAHE เต็มไปด้วย
ลายเส้นแนวนอนที่ถูกขยาย (ตรงกับตัวเลข +76% ในหัวข้อ 11.3) การเพิ่มช่องที่มี noise
ถูกขยายเข้าไปคู่กับภาพดิบ จึงไปกลบสัญญาณบางๆ ของ mild

ข้อสังเกตเพิ่ม: เทียบ R10 (ช่อง 3 = gray) กับ R11 (ช่อง 3 = mask) ที่ best_epoch
ใกล้กัน (7 vs 8) พบว่าการเพิ่มช่อง mask ทำ mild ตกจาก 0.478 → 0.326 — **ทิศทางเดียว
กับ R9** แต่ยังไม่ใช่หลักฐานหนักแน่นพอจะสรุปเป็นกฎ เพราะรันที่ควรยืนยันเรื่องนี้
แบบแยกเดี่ยว (R12) ใช้ไม่ได้

### 12.6 destriping (R5, R6) — ผลที่ดีที่สุดของรอบนี้

**วิธีที่ตั้งใจไม่ใช้**: FFT notch filter ตัดความถี่แนวตั้ง — ใช้กับงานนี้ไม่ได้
เพราะเส้น endplate ก็เป็นโครงสร้างแนวนอน การตัดความถี่แนวตั้งจะลบสิ่งที่ต้องวัด
ทิ้งไปพร้อม noise

**วิธีที่ใช้**: ลบเฉพาะ "ค่าคงที่ที่เลื่อนไปทั้งแถว"
1. หาความสว่างเฉลี่ยของพิกเซลกระดูกแต่ละแถว → โปรไฟล์แนวตั้ง
2. median filter บนโปรไฟล์ (หน้าต่าง 5 แถว)
3. ส่วนต่าง = การกระตุกของแถวนั้น → ลบทิ้ง

ใช้ **median** ไม่ใช่ค่าเฉลี่ยเคลื่อนที่ เพราะ median รักษาขอบแบบขั้นบันไดไว้ได้
ขณะที่ลบค่าโดดของแถวเดี่ยวๆ ออก — endplate ซึ่งเป็นการเปลี่ยนความสว่างแบบขั้นบันได
จึงรอด

| | พลังงานความถี่สูงรายแถว | ความชันขอบ endplate (p99) |
|---|---|---|
| ต้นฉบับ | 0.362 | 24.23 |
| **destripe** | **0.106 (−71%)** | 22.82 (−5.8%) |
| clahe | 0.638 | — |
| destripe_clahe | 0.209 (−67% เทียบ clahe) | — |

ลบการกระตุกได้ 71% แลกกับขอบ endplate อ่อนลง 5.8% และค่าความสว่างเปลี่ยนเฉลี่ย
เพียง 1.38 ระดับจากสเกล 0-255

**ผล R5 คือจุดสูงสุดของโปรเจกต์สำหรับ mild**:

| | R0 (ตั้งต้น) | R2 (augment) | **R5 (+destripe)** |
|---|---|---|---|
| **mild** | 0.217 | 0.543 | **0.630** |
| **moderate** | 0.333 | 0.392 | **0.471** |
| severe | 0.771 | 0.771 | 0.714 |
| normal | 0.955 | 0.908 | 0.884 |
| macro F1 | 0.567 | 0.570 | 0.567 |
| AUC | 0.861 | 0.941 | 0.934 |

**mild 0.217 → 0.630 = จาก 10 เป็น 29 ปล้องจาก 46 (ดีขึ้น 2.9 เท่า)** และ
**moderate ดีขึ้นพร้อมกัน** — ก่อนหน้านี้ต้องเลือกอย่างใดอย่างหนึ่งเสมอ

**macro F1 แทบไม่ขยับเลยทั้งสามคอลัมน์ (0.567 / 0.570 / 0.567)** ทั้งที่โปรไฟล์
เปลี่ยนไปสิ้นเชิง — เป็นตัวอย่างที่ชัดที่สุดว่าตัวชี้วัดรวมมองไม่เห็นอะไรเลย

### 12.7 unsharp และ flatten (R7, R8, R13)

**สมมติฐาน**: mild ต้องการเห็นเส้น endplate ชัดขึ้น เพราะ Genant grade 1 คือความสูง
ลดเพียง 20-25% ต้องเพ่งขอบถึงจะแยกออก

**การเบลอกับพื้นหลังดำ — ปัญหาที่ต้องแก้ก่อน**: ทั้ง unsharp และ flatten ต้องเบลอภาพ
ถ้าเบลอตรงๆ ค่า 0 ของพื้นหลังจะไหลเข้าผสมกับกระดูกริมขอบ พอเอาไปลบจะเกิดขอบสว่าง
ปลอม **ตรงตำแหน่ง endplate พอดี**

แก้ด้วย normalized convolution (เบลอทั้งภาพที่คูณ mask และตัว mask แล้วหารกัน):

| | halo ที่ริมขอบ |
|---|---|
| ภาพต้นฉบับ (ค่าธรรมชาติ) | −6.69 |
| **เบลอแบบกัน mask (ที่ใช้จริง)** | **−6.11** ✅ |
| เบลอแบบธรรมดา | **+2.24** ❌ กลับทิศ = สร้างขอบสว่างปลอม |

| | ขอบ p99 | แสงพื้นหลัง sd |
|---|---|---|
| ต้นฉบับ | 24.23 | 4.34 |
| unsharp | **46.73 (+93%)** | 4.38 |
| flatten | 24.21 | **1.59 (−63%)** |

**ผลไม่สนับสนุนสมมติฐาน** — R8 (destripe+unsharp) ทำ mild ตกจาก 0.630 เหลือ 0.500
ขณะที่ moderate เท่าเดิม และ R7 (unsharp เดี่ยว) ได้ mild เพียง 0.543 เท่ากับ R2
ที่ไม่ได้ทำอะไรเลย

สิ่งเดียวที่ได้คือ **AUC 0.942 ซึ่งเป็นค่าสูงสุดของโปรเจกต์** (แซง R2 ที่ 0.941
เล็กน้อยซึ่งอยู่ในโซนเสมอ)

**สมมติฐานสำรองก็ไม่ผ่านเช่นกัน** — ตั้งไว้ว่าถ้าสัญญาณของ mild เป็นความถี่ต่ำ
(ความสูงลดทั้งปล้อง) ไม่ใช่ความคมของขอบ การลบความถี่ต่ำทิ้งด้วย `flatten` ควรทำ
mild แย่ลงชัดเจนกว่า unsharp

R13 (destripe+flatten) ได้ mild = **0.500 เท่ากับ R8 เป๊ะ** ทั้งที่แก้ภาพไปคนละทิศ
ทางกันโดยสิ้นเชิง (ตัวหนึ่งเพิ่มความถี่สูง อีกตัวลบความถี่ต่ำ)

**ข้อสรุปที่ตรงกว่า**: ไม่ใช่เรื่องความถี่ไหนถูกหรือผิด แต่คือ **การแต่งภาพเพิ่ม
บน destripe ไม่ว่าทิศทางใด ก็ดึง mild กลับลงมาที่ราว 0.50 เหมือนกันหมด** —
`destripe` เดี่ยวๆ อยู่ที่จุดที่ดีที่สุดแล้ว การกรองเพิ่มมีแต่จะรบกวน

สอดคล้องกับข้อค้นพบ 13.3: สิ่งที่ได้ผลกับข้อมูลชุดนี้คือ "การลบสิ่งที่ไม่ควรมี"
ไม่ใช่ "การเน้นสิ่งที่มีอยู่"

## 13. ข้อค้นพบหลักของรอบที่ 2

### 13.1 augmentation คือตัวแปรที่มีผลมากที่สุดเท่าที่เคยทดสอบมา

R0 → R2: **AUC +8.0 pp** (0.861 → 0.941, เกินเกณฑ์ 5 pp), **mild +32.6 pp**
(0.217 → 0.543), moderate +5.9 pp โดย **severe เท่าเดิมที่ 0.771**

เสียเฉพาะ normal 0.955 → 0.908 ซึ่งเป็นคลาสที่ง่ายอยู่แล้วและมีตัวอย่าง 1,548 ปล้อง

AUC 0.941 สูงกว่าทุกการทดลองในภาคที่ 1 รวมถึงโจทย์ binary ที่ยุบเหลือ 2 คลาส (0.937)
ทั้งที่ยังตอบ 4 คลาสเต็ม

### 13.2 destriping ต่อยอดได้อีก และเป็นการปรับปรุง mild ที่ดีที่สุด

> ⚠️ **"ต่อยอดได้อีก" ถูกพิสูจน์แล้วว่าไม่จริง — ดูหัวข้อ 20 และ 26.2**
> ทุกชุดที่เอา destripe ไปต่อหน้าตัวอื่น (`destripe_clahe`, `destripe_unsharp`,
> `destripe_flatten`) อยู่ครึ่งล่างของตารางเมื่อวัดด้วย 2 seed และผู้ชนะจริงคือ
> `flatten` เดี่ยวๆ — destripe ยังชนะเรื่อง AUC แต่ไม่ใช่ฐานที่ควรต่อยอด

R2 → R5: **mild +8.7 pp และ moderate +7.9 pp พร้อมกัน** (แลกกับ severe −5.7)

รวมจากจุดตั้งต้น R0 → R5: **mild +41.3 pp, moderate +13.8 pp**

### 13.3 image preprocessing แบบปรับคอนทราสต์ไม่ช่วย — แต่การลบ artifact ช่วย

`normalize`, `clahe`, `unsharp`, การรวมช่องสี — ทั้งหมดอยู่ในโซนเสมอหรือแย่ลง

สิ่งเดียวที่ได้ผลคือ `destripe` ซึ่ง**ไม่ได้ปรับแต่งอะไร แต่ลบสิ่งที่ไม่ควรมีอยู่ออก**

บทเรียน: ก่อนจะปรับแต่งภาพ ควรวัดก่อนว่าในภาพมี artifact อะไรอยู่จริง — การเพิ่ม
คอนทราสต์บนภาพที่มี noise ซ่อนอยู่ ทำให้ noise เด่นขึ้นพร้อมกับสัญญาณ

### 13.4 การป้อนข้อมูล "รูปทรง" ให้โมเดลอย่างชัดเจน มีแนวโน้มทำให้ mild แย่ลง

พบสัญญาณ 2 จุดที่ชี้ไปทางเดียวกัน (R9 ฟีเจอร์เรขาคณิต และ R11 ช่อง mask) อธิบายได้
ด้วยการวัดในหัวข้อ 11.1 ว่ารูปทรงแยก mild จาก normal ไม่ได้

**ยังไม่ใช่หลักฐานหนักแน่นพอจะสรุปเป็นกฎ** เพราะรันที่ควรยืนยันแบบแยกเดี่ยว (R12)
ถูก early stopping ตัดจนใช้ไม่ได้

### 13.5 macro F1 ไม่ไวพอที่จะใช้เป็นตัวชี้วัดหลักของงานนี้

macro F1 ของ **13 การทดลองทั้งหมดอยู่ในช่วง 0.491-0.585** และเกือบทุกคู่ตัดสินว่า
"เสมอ" ตามกฎ 5 pp ขณะที่ AUC ต่างกันถึง 8 pp และ recall ของ mild ต่างกันถึง 3 เท่า

กรณีที่ชัดที่สุด: R0 กับ R5 ได้ macro F1 เท่ากันเป๊ะ (0.567) แต่ mild ต่างกัน
0.217 vs 0.630

**ต้องรายงาน AUC และ recall ราย grade ควบคู่เสมอ** ไม่ใช่ macro F1 ตัวเดียว

## 14. การแก้ข้อสรุปจากภาคที่ 1

### 14.1 แก้หัวข้อ 5.3 — mild ไม่ใช่ข้อจำกัดเชิงโครงสร้างอย่างที่สรุปไว้

ข้อความเดิม: *"ปัญหาน่าจะมาจากตัวอย่างที่น้อยเกินไป ... ไม่น่าแก้ได้ด้วยเทคนิค
การเทรน ต้องการข้อมูลเพิ่ม"*

**ข้อสรุปนั้นไม่ผิดในตอนนั้น** เพราะหลักฐานที่มีมาจาก 4 ทาง (เปลี่ยน crop, เพิ่ม
metadata, ยุบคลาส, เปลี่ยน backbone) ซึ่ง**ไม่มีทางไหนเป็น regularization เลย** และ
หัวข้อ 6.6 ก็ระบุเองว่ายังไม่เคยทดสอบ augmentation

**หลักฐานใหม่**: mild ขึ้นจาก 0.217 เป็น 0.630 ด้วยเทคนิคการเทรนล้วนๆ ไม่ได้เพิ่ม
ข้อมูลแม้แต่ปล้องเดียว

**ข้อสรุปใหม่**: ส่วนใหญ่ของปัญหา mild มาจาก **overfit** ไม่ใช่จากจำนวนตัวอย่าง
อย่างเดียว — เป็นการเติมช่องว่างที่เอกสารเว้นไว้เอง ไม่ใช่การหักล้างเหตุผลเดิม

(ยังเหลือ 17 จาก 46 ปล้องที่จับไม่ได้ ซึ่งส่วนนั้นอาจยังเป็นข้อจำกัดของข้อมูลจริง)

### 14.2 แก้หัวข้อ 3.3 — เกณฑ์เลือกโมเดลด้วย macro F1

ข้อความเดิม: *"เกณฑ์เลือกโมเดล: macro F1 บนชุด val"* พร้อมเหตุผลว่า accuracy ใช้
ไม่ได้กับข้อมูลไม่สมดุล

เหตุผลนั้นถูก แต่ macro F1 ไม่ใช่ทางเลือกที่ดีที่สุด — วัดจาก history จริงของ 11
การทดลอง (ช่วงที่ราบแล้ว epoch ≥ 5):

| เกณฑ์ | sd |
|---|---|
| val macro F1 | **2.29 pp** |
| (F1 + AUC)/2 | 1.22 pp |
| val AUC | **0.61 pp** |

ความแกว่ง 2.29 pp ของ macro F1 **กว้างกว่าเกณฑ์ 2 pp ที่ตั้งไว้ว่า "ถือว่าเสมอ"**
ในหัวข้อ 3.5 — คือความผันผวนภายในการรันครั้งเดียว ใหญ่กว่าเส้นแบ่งที่ใช้ตัดสินว่า
ผลต่างระหว่างการทดลองมีความหมายหรือไม่

เพิ่มตัวเลือก `train.select_metric` แล้ว (ค่าเริ่มต้นยังเป็น `f1` เพื่อไม่ให้
config เก่าเปลี่ยนพฤติกรรม)

### 14.3 เพิ่มเติมหัวข้อ 6.6 — ตอบแล้วบางส่วน

*"ยังไม่ได้ทดสอบ augmentation และ image preprocessing"* — ทดสอบแล้วในภาคนี้
augmentation ได้ผลชัด ส่วน preprocessing แบบปรับคอนทราสต์ไม่ได้ผล แต่การลบ artifact
(destriping) ได้ผล

## 15. ข้อจำกัดของรอบที่ 2

### 15.1 ยังเป็น seed เดียวทุกการทดลอง

ข้อจำกัด 6.1 ของภาคที่ 1 ยังคงอยู่ทั้งหมด ผลของ augmentation (+8.0 pp AUC,
+32.6 pp mild) และ destriping (+8.7 pp mild) ใหญ่เกินระดับ noise ที่วัดได้มาก
จึงน่าเชื่อถือ **แต่ผลของ preprocessing และช่องสีที่อยู่ในช่วง 1-3 pp ยังยืนยันไม่ได้**

### 15.2 เสียการทดลองไป 2 ตัวเพราะ early stopping ไม่เสถียร

R6 และ R12 ถูกตัดจบที่ epoch 3 และ 2 เพราะ val macro F1 พีคหลอกแล้วไม่ผ่านอีก
3 รอบ ทั้งที่ val_AUC ยังไต่ขึ้นอยู่ (R6: val_AUC สูงสุดที่ epoch 6 ซึ่งเป็น epoch
สุดท้ายพอดี)

การเปลี่ยนเกณฑ์เป็น `f1_auc` แก้ได้ 1 ใน 2 กรณี (จำลองแล้ว) — อีกกรณีต้องเพิ่ม
patience ด้วย เพราะปัญหาที่แท้จริงคือ patience 3 สั้นเกินไปเมื่อเทียบกับความแกว่ง
ที่เหลือ 1.22 pp

**ข้อเสนอโปรโตคอลสำหรับรอบต่อไป**: `epochs: 15, patience: 15` (ไม่หยุดก่อนกำหนดเลย)
+ `select_metric: f1_auc` — ทุกการทดลองได้ compute เท่ากันเป๊ะ ตัดตัวแปร "หยุดตอนไหน"
ออกจากการเปรียบเทียบทั้งหมด

### 15.3 ยังไม่ได้ทำ Grad-CAM กับโมเดลที่ผ่าน augmentation

สมมติฐานที่ยังไม่ได้ตรวจ: การเลื่อนตำแหน่งใน `strong` น่าจะเป็นสาเหตุที่ mild ดีขึ้น
เพราะทำให้กระดูกไม่อยู่กลางกรอบเป๊ะทุกใบ โมเดลจึงยึดตำแหน่งในกรอบเป็นสัญญาณไม่ได้ —
ซึ่งตรงกับปัญหา "มองมุมดำ" ที่พบในหัวข้อ 4.3

หลักฐานทางอ้อมที่สนับสนุน: `intensity` (ไม่มีการเลื่อน) ได้ mild เพียง 0.391
ขณะที่ `standard` (เพิ่มการหมุน/เลื่อน) ได้ 0.413 และ `strong` ได้ 0.565

### 15.4 การเทียบ R7-R8 กับแถวอื่นใช้เกณฑ์เลือกโมเดลต่างกัน

R7-R8 ใช้ `f1_auc` แถวอื่นใช้ `f1` — ตรวจด้วยการจำลองแล้วว่าแถวหลักที่เอาไปเทียบ
(R2, R5) เลือก epoch เดียวกันภายใต้ทั้งสองเกณฑ์ แต่ยังเป็นความไม่สม่ำเสมอที่ควรแก้
ด้วยการรันใหม่ทั้งชุดภายใต้โปรโตคอลเดียวกัน

### 15.5 ความผิดพลาดเชิงกระบวนการที่เกิดขึ้นและวิธีป้องกัน

- **แก้ไฟล์ source ระหว่างที่การเทรนกำลังรัน** ทำให้ baseline 50ep ตายกลางคัน
  (เสียเวลา ~30 นาที) สาเหตุ: บน Windows PyTorch สร้าง DataLoader worker ด้วยวิธี
  spawn ซึ่ง **re-import โมดูลใหม่ทุก epoch** worker ที่เกิดหลังแก้ไฟล์จึงได้โค้ด
  เวอร์ชันใหม่ที่ไม่ตรงกับ object ที่ถูก pickle ส่งไป
  → **ห้ามแก้ไฟล์ใน `src/` หรือ `scripts/` ระหว่างที่มีการเทรนรันอยู่**

  encoding เป็น cp1252 ซึ่งเขียนภาษาไทยไม่ได้ ทำให้ `print` ภาษาไทยใน `train.py`
  ทำให้โปรแกรมตายทันที
  → ตั้ง `$env:PYTHONIOENCODING="utf-8"` ก่อนรันเสมอเมื่อจะเก็บ log

## 19. โครงสร้างที่เพิ่มเข้ามาในโค้ด

### 19.1 ชุด augment ที่แตะรูปทรง — `shape`, `standard_shape`, `strong_shape`

ภาคที่ 2 หัวข้อ 12.2 ระบุว่า flip / scale / elastic **ห้ามใช้** ด้วยเหตุผลเชิงทฤษฎี
(flip แนวนอนสลับ anterior wedge เป็น posterior wedge, scale ทำลาย aspect ratio,
elastic บิดรูปทรงซึ่งเป็นสิ่งที่ label อ้างอิงโดยตรง)

รอบนี้ตัดสินใจ **ทดสอบข้อห้ามนั้นแทนที่จะเชื่อ** เพราะข้อห้ามที่ไม่เคยวัด ก็คือ
สมมติฐานที่ยังไม่ได้ตรวจสอบ — จึงเพิ่ม 3 ฟังก์ชันย่อยและ 3 preset:

| ฟังก์ชันย่อย | พารามิเตอร์ |
|---|---|
| `random_flip` | p_h = 0.5, p_v = 0.5 |
| `random_scale` | 0.85–1.15, p = 0.5 |
| `random_elastic` | alpha = 8.0, sigma = 12.0, p = 0.5 |

| preset | ประกอบด้วย | ตั้งใจตอบคำถามอะไร |
|---|---|---|
| `shape` | flip + scale + elastic ล้วนๆ | ข้อห้ามถูกหรือผิด — ต้องมีชุดนี้ ดูจาก `standard_shape` อย่างเดียวสรุปไม่ได้ เพราะมีของที่ช่วยกับของที่ทำลายปนกัน |
| `standard_shape` | intensity + geometric + shape | เติม shape ให้ชุดกลางแล้วได้อะไร |
| `strong_shape` | strong + shape | เติม shape ให้ชุดที่แรงอยู่แล้วยังได้ผลเหมือนกันไหม |

การเรียงลำดับใน `standard_shape` จงใจให้ transform ที่ใช้ interpolation ทั้งหมด
(rotate / scale / elastic) อยู่ติดกันท้ายสุด ภาพจึงผ่านการเกลี่ยพิกเซลเป็นชุดเดียว
ไม่สลับกับการโรย noise ไปมาจนเนื้อภาพนุ่มกว่าที่ควรเป็น

วัดความแรงของ `strong_shape` ได้: โอกาสที่ภาพจะไม่ถูกแตะเลยเหลือ **0.14%** เฉลี่ยโดน
**4.2 transform ต่อภาพ** (เทียบกับ `standard_shape` ที่ 0.77% และ 3.6 ตัว)

### 19.2 ขยายชุด train แบบ "อบลงไฟล์" — `scripts/build_augmented_trainset.py`

เขียนภาพที่ผ่าน preprocess + pad + augment แล้วลงดิสก์จริง เป็น variant ใหม่ที่
`train.py` ใช้ได้ทันทีโดยไม่ต้องแก้โค้ดสักบรรทัด

|  | `data.augment` (on-the-fly) | ไฟล์นี้ (offline) |
|---|---|---|
| ไฟล์บนดิสก์ | 8,409 ใบ | 84,090 ใบ (ที่ factor 10) |
| สุ่มตอนไหน | ทุกครั้งที่หยิบภาพ | ครั้งเดียวตอนสร้าง แล้วแช่แข็ง |
| เวอร์ชันต่อ 1 ภาพ | ไม่จำกัด (ใหม่ทุก epoch) | ตายตัวเท่ากับ factor |
| ชี้ให้คนอื่นดูได้ | ไม่ได้ | ได้ เปิดโฟลเดอร์ดูได้เลย |

**กับดัก 3 ข้อที่ออกแบบมากันโดยเฉพาะ**

1. **จำนวนรอบเฟ้อ 10 เท่าโดยไม่รู้ตัว** — 1 epoch บนข้อมูล 84,090 ใบ = 10 epoch เดิม
   ถ้ารัน 15 epoch เหมือนเดิมแล้วเอาไปเทียบตารางเก่า ผลจะแปลว่า "เทรนนานกว่า 10 เท่า"
   ไม่ใช่ "การขยายข้อมูลช่วย" -> สคริปต์พิมพ์ epoch ที่เทียบเท่าให้ดูตอนจบ
2. **val/test ต้องไม่ถูก augment** แต่ต้องไม่เป็นคนละ distribution กับ train
   -> เขียน val/test ออกมาเหมือนกันทุกอย่าง (ผ่าน preprocess + pad ขนาดเดียวกัน)
   ต่างกันแค่ไม่ augment และไม่คูณ (1 เท่าเสมอ ไม่ว่าตั้ง factor เท่าไหร่)
3. **augment ซ้ำสองชั้น** — ถ้า config ที่เอาไปใช้ยังตั้ง `data.augment` ไว้อีก
   ภาพจะโดน augment ทับอีกรอบ -> สคริปต์เขียน config ตัวอย่างที่ตั้ง preprocess/augment
   เป็น `none` ไว้ให้ด้วย

ลำดับที่ bake ลงไฟล์ตรงกับ `transforms.py` เป๊ะ:
`เปิดไฟล์ -> preprocess -> resize/pad 224 -> augment -> เซฟ`
(augment อยู่หลัง pad โดยตั้งใจ เพราะ crop ตัดชิดตัวกระดูก ถ้าหมุนตอนยังไม่ pad
มุมกระดูกจะถูกตัดหายทันที)

### 19.3 ขยายด้วยการ "ทำซ้ำแถว" — `scripts/make_repeated_trainset.py`

เขียนขึ้นหลังพบข้อบกพร่องเชิงโครงสร้างของวิธี 19.2 (รายละเอียดที่หัวข้อ 23.2)

**ปัญหาที่พบ**: การอบ augment ลงไฟล์เฉพาะสำเนาที่ 1-9 ทำให้เกิดความไม่สมมาตร

```
normal   สำเนาที่ 0 อย่างเดียว  ->  augment สุ่มสดตอนเทรน        1 ชั้น
damaged  สำเนาที่ 1-9 (90%)     ->  augment ที่อบไว้ + สุ่มสดอีก   2 ชั้น
```

วัดจากปล้องผิดปกติจริง 40 ใบ: 1 ชั้นห่างจากภาพจริง **23.24 ระดับ** ส่วน 2 ชั้น
**40.75 ระดับ** = บิดเบือนมากกว่า **1.75 เท่า** ผลคือโมเดลเรียนว่า
"damaged = ปล้องที่บิดเบี้ยวหนัก" แต่ชุด test ไม่ถูก augment เลย ปล้อง mild จริง
จึงไม่เหมือน damaged ที่โมเดลรู้จัก -> ทายว่า normal

ไฟล์นี้แก้ที่ต้นเหตุ: **ทุกแถวชี้ไฟล์ต้นฉบับเดียวกัน** ไม่มีอะไรอบไว้ล่วงหน้า
augment สุ่มสดจึงทำงานกับทุกคลาสเท่ากัน 1 ชั้นเสมอ แต่ยังได้ประโยชน์ที่ตั้งใจคือ
คลาสน้อยถูกหยิบมาอัปเดต gradient N เท่าต่อ epoch ด้วยหน้าตาที่ต่างกันทุกครั้ง

ผลพลอยได้: ไม่เขียนไฟล์ภาพใหม่เลยสักไฟล์ (ประหยัด ~190 MB และเวลาสร้าง ~10 นาที)

| variant | แถว train | normal | mild | moderate | severe |
|---|---|---|---|---|---|
| `xray_masked` (เดิม) | 8,409 | 7,704 | 224 | 286 | 195 |
| `xray_masked_rep1-10-10-10` | 14,754 | 7,704 | 2,240 | 2,860 | 1,950 |

### 19.4 `downsample_mode: dynamic`

โครง `DownsampledNormalSampler` มีมาตั้งแต่ภาคที่ 1 แต่ไม่เคยได้รัน รอบนี้เพิ่มโหมด
`dynamic` = **สุ่มปล้อง normal ชุดใหม่ทุก epoch** แทนที่จะล็อกชุดเดียวตลอดการเทรน

**ข้อค้นพบ — 4 ข้อที่พลิกความเชื่อเดิม**

**1. ข้อห้าม flip / scale / elastic ในหัวข้อ 12.2 ผิด**

ทุกชุดที่มี `shape` อยู่ครึ่งบนของตาราง และ `shape` เดี่ยวๆ (ซึ่งประกอบด้วย
transform ที่ "ห้าม" ล้วนๆ) ชนะ `standard`, `geometric`, `none`, `intensity`
— คือชนะทุกชุดที่ปฏิบัติตามข้อห้ามอย่างเคร่งครัด ยกเว้น `strong`

เหตุผลที่ทฤษฎีเดิมผิด (ตีความ): ข้อห้ามตั้งอยู่บนสมมติฐานว่าโมเดลกำลังเรียนรูปทรง
ที่แม่นยำอยู่แล้ว การบิดรูปทรงจึงเป็นการทำลายสัญญาณ แต่หลักฐานในภาคที่ 2 (หัวข้อ 13.4)
และภาคนี้ชี้ว่าโมเดล **ยังไม่ถึงขั้นนั้น** — ปัญหาหลักคือ overfit ไม่ใช่ความละเอียด
ของรูปทรง การบิดรูปทรงจึงทำหน้าที่เป็น regularizer ที่ได้ผล และความเสียหายต่อ label
น้อยกว่าประโยชน์ที่ได้

**2. `intensity` แพ้ `none` ทั้ง 2 seed**

การรบกวนความเข้มอย่างเดียวแย่กว่าไม่ทำอะไรเลย (0.548 vs 0.565) — สิ่งที่ช่วยคือ
**การรบกวนเชิงเรขาคณิต** ไม่ใช่ความเข้ม ซึ่งตรงข้ามกับที่ภาคที่ 2 ออกแบบไว้
(`intensity` ถูกวางเป็น "ชุดที่ควรลองก่อนเพื่อน เพราะปลอดภัยที่สุด")

**3. เพดานของการรบกวนเรขาคณิต**

| ฐาน | ไม่เติม shape | เติม shape | ส่วนต่าง |
|---|---|---|---|
| standard | 0.577 | 0.604 | **+2.7 pp** |
| strong | 0.614 | 0.605 | **−0.9 pp** |

เติม `shape` ให้ `standard` ช่วย แต่เติมให้ `strong` กลับทำให้แย่ลง เพราะ `strong`
มี rotate ±10° / shift ±7% ที่ p=0.7 แรงอยู่แล้ว การเติม scale/elastic/flip เข้าไปอีก
ถึงจุดอิ่มตัว — **มีเพดานของปริมาณการรบกวนเรขาคณิตที่โมเดลรับได้**

**4. `strong` ชนะ macro F1 แต่ชุด `*_shape` ชนะการจับคลาสน้อย**

`strong_shape` ได้ mild 0.413 / moderate 0.598 / AUC 0.938 สูงกว่า `strong` ทุกตัว
แต่ macro F1 ต่ำกว่า เพราะ normal recall ตกจาก 0.966 เหลือ 0.931 (= false positive
บนคลาสที่มี 1,548 ใบ ซึ่งกดค่าเฉลี่ยลงมากกว่าที่การจับ mild เพิ่มขึ้นจะชดเชยได้)

**นี่คือหลักฐานอีกชิ้นของข้อสรุป 13.5 ว่า macro F1 ไม่ไวพอสำหรับงานนี้** — ถ้าเป้าหมาย
คือการคัดกรอง (จับให้เจอ) ควรเลือก `strong_shape` ไม่ใช่ `strong`

## 23. การขยายชุดข้อมูล 10 เท่า — ปิดจ๊อบแล้ว

### 23.1 ผลครบ 3 seed

เทียบ `flatten`+`strong` บนชุดเดิม vs ชุดที่อบ augment ลงไฟล์ 10 เท่า
(ทั้งสองฝั่งเปิด `augment: strong` สุ่มสดเหมือนกัน ต่างกันแค่ชุดข้อมูล)

| ตัวชี้วัด | ชุดเดิม | ชุด 10x | ต่าง | เกิน noise? |
|---|---|---|---|---|
| macro F1 | 0.622 ± 0.028 | 0.592 ± 0.026 | −0.030 | **ไม่** |
| AUC | 0.917 ± 0.004 | 0.928 ± 0.017 | +0.010 | **ไม่** |
| mild recall | 0.319 ± 0.070 | 0.319 ± 0.100 | 0.000 | ไม่ |
| moderate recall | 0.444 ± 0.069 | 0.366 ± 0.069 | −0.078 | **ไม่** |
| severe recall | 0.724 ± 0.044 | 0.724 ± 0.033 | 0.000 | ไม่ |

**ไม่มีตัวชี้วัดไหนต่างเกิน noise เลยสักตัว** — ข้อได้เปรียบ AUC ที่เห็นตอนมี 2 seed
หายไปเมื่อ seed 44 เข้ามา (0.908) ทำให้ sd โตกว่าความต่างเอง

สิ่งเดียวที่ต่างจริงและสม่ำเสมอ: **best epoch** ชุดเดิม 39 / 35 / 49 · ชุด 10x 3 / 5 / 5
= ต่างกันราว 8 เท่า สม่ำเสมอทั้ง 3 seed

### 23.2 ทำไมคูณข้อมูลแล้วไม่ช่วย — 3 เหตุผลที่ตรวจแล้ว

**เหตุผลที่ 1 — น้ำหนักคลาสหักล้างการคูณข้อมูลทิ้งทั้งหมด**

สูตรน้ำหนักที่ใช้คือ `w_c = N / (K * n_c)` ซึ่งทำให้ `n_c * w_c = N / K` เท่ากันทุกคลาส
**เสมอ ไม่ว่าจะคูณข้อมูลเท่าไหร่**

```
คูณ mild 10 เท่า  ->  n_mild เพิ่ม 10 เท่า  ->  w_mild ลด 10 เท่า
                  ->  น้ำหนักรวมของคลาส mild เท่าเดิมเป๊ะ
```

วัดจริงในโจทย์ binary: น้ำหนักต่อ 1 ตัวอย่างของคลาส damaged ลดจาก **5.96 เหลือ 1.05**
(5.7 เท่า) = สมดุลที่โมเดลเห็นเหมือนเดิมทุกประการ แต่แต่ละใบถูก "เจือจาง" ลง

**เหตุผลที่ 2 — ไม่ได้เพิ่มความหลากหลายจริง**

ยังเป็นปล้อง mild ชุดเดิม 224 ปล้อง ไม่มีเคสใหม่แม้แต่ใบเดียว และเนื่องจากทั้งสองฝั่ง
เปิด `augment: strong` สุ่มสดเหมือนกัน ความหลากหลายระดับพิกเซลจึงเป็นอนันต์อยู่แล้ว
**ทั้งคู่** สำเนาแช่แข็ง 10 ใบจึงซ้ำซ้อนกับสิ่งที่ on-the-fly ทำอยู่แล้ว

**เหตุผลที่ 3 — มันเห็นภาพไม่ซ้ำ *น้อยกว่า* ชุดเดิม**

นับ "ภาพไม่ซ้ำที่โมเดลเห็นจริง" = แถว x epoch ที่พีค (เพราะ augment สุ่มใหม่ทุกครั้งที่หยิบ):

| | แถว/epoch | epoch ที่พีค | ภาพไม่ซ้ำที่เห็นจริง |
|---|---|---|---|
| ชุดเดิม | 8,409 | 39 / 35 / 49 | **~345,000** |
| ชุด 10x | 84,090 | 3 / 5 / 5 | **~64,000** |

**ชุดเดิมเห็นภาพไม่ซ้ำมากกว่า 5.4 เท่า** — การอบ augment ลงไฟล์เพิ่มแค่ "ความถี่ใน
การหยิบซ้ำต่อ epoch" -> พีคเร็วขึ้น -> early stopping ตัดจบก่อน -> เห็นภาพรวมน้อยลง

## 24. หลักฐานว่าชนเพดานข้อมูล ไม่ใช่เพดานวิธี

รวมผลการทดลอง multiclass ทั้งหมด **79 รัน**:

| ข้อเท็จจริง | ตัวเลข |
|---|---|
| mild recall มัธยฐานของทั้ง 79 รัน | **0.304** |
| รันที่ได้ mild recall >= 0.50 | **13 / 79 = 16%** |
| ปล้อง mild ในชุด train | **224** |
| ปล้อง mild ในชุด test | **46** (ทายถูกเพิ่ม 1 ใบ = +2.2 pp) |

5 อันดับสูงสุดกระจัดกระจาย ไม่ใช่สูตรเดียวที่ชนะซ้ำได้ และ 2 ใน 5 เป็นรันที่หยุดที่
epoch 2-3 ซึ่งตัวเลขใช้ไม่ได้

**ข้อสรุป**: augmentation สร้างการแปรผัน "รอบๆ" 224 ปล้องเดิมได้ แต่บอกไม่ได้ว่า
ปล้องที่ 225 ของคนไข้คนใหม่หน้าตาเป็นยังไง — ไม่ว่าจะคูณกี่เท่าก็ตาม
**ทางเดียวที่แก้ตรงเพดานคือเก็บเคส mild เพิ่ม**

## 25. รอบที่ 4 — โจทย์ binary และการเทียบวิธีทำให้สมดุล

### 25.1 ทำไมทำ

จากหัวข้อ 24 เมื่อชนเพดานข้อมูลของโจทย์ 4 คลาสแล้ว ทางที่เหลือที่ **ไม่ต้องเก็บ
ข้อมูลเพิ่ม** คือลดความละเอียดของโจทย์ ภาคที่ 1 หัวข้อ 5.2 เคยยืนยันว่าการยุบเป็น
binary ช่วยการตรวจจับได้จริงทุกระดับ รอบนี้ทำซ้ำด้วยโปรโตคอลใหม่ + preprocess/augment
ที่ชนะ (`flatten` + `strong`) และเพิ่มคำถามใหม่: **วิธีทำให้ข้อมูลสมดุลแบบไหนดีที่สุด**

โจทย์: `normal (grade 0)` vs `damaged (grade 1-3)` — train 7,704 : 705 · test 1,548 : 132

### 25.2 เจ็ดเงื่อนไข x 2 seed

| `orig` | น้ำหนักคลาสอย่างเดียว (ตัวคุม) | 8,409 | เปิด |

| rep10_ds11 | **0.850 ± 0.013** | 0.955 | 51 | **12** | 0.228 | 0.706 |

### 25.4 ข้อค้นพบที่สำคัญที่สุดของภาคนี้

**macro F1 จัดอันดับกลับหัวกับสิ่งที่งานนี้ต้องการ**

ดูตารางเดิมโดยเรียงตามคอลัมน์ "ปล่อยหลุด" แทน จะได้อันดับ **ตรงกันข้ามเกือบสมบูรณ์**:

| เรียงตาม macro F1 | เรียงตามจำนวนที่ปล่อยหลุด (น้อย = ดี) |
|---|---|
| 1. rep10_ds11 (0.850) | 1. **orig (31.5 ใบ)** |
| 2. x10 (0.850) | 2. ds11 (37) |
| ... | 3. x10 (42.5) |
| 6. ds11 (0.828) | ... |
| 7. **orig (0.827)** | 7. rep10_ds11 (51) |

เหตุผลเชิงเลข: normal มี 1,548 ใบ ส่วน damaged มี 132 ใบ การลด false positive
50 ใบ (จาก 61.5 -> 12) ดัน F1 ของคลาส normal ขึ้นได้มากกว่าที่การปล่อยหลุดเพิ่ม
20 ใบจะกด F1 ของคลาส damaged ลง — **แม้จะเป็นการพลาดผู้ป่วยจริงเพิ่ม 20 คน**

`orig` (น้ำหนักคลาสอย่างเดียว ไม่ขยายข้อมูลเลย) จับ damaged ได้ดีที่สุดทุกระดับ
mild 0.511 · moderate 0.824 · severe 1.000 และปล่อยหลุดน้อยที่สุด — แต่ได้ macro F1
ต่ำสุดในตาราง

**-> สำหรับงานคัดกรอง `orig` คือโมเดลที่ดีที่สุด ไม่ใช่ `rep10_ds11`**
และต้องรายงานตัวเลขนี้พร้อมคำอธิบาย ไม่ใช่รายงาน macro F1 เฉยๆ

**ทุกวิธีที่ขยายข้อมูลคลาสน้อย ทำให้จับคลาสน้อยได้แย่ลง — โดยไม่มีข้อยกเว้น**

| วิธี | mild recall |
|---|---|
| ไม่ขยายเลย (`orig`) | **0.511** |
| down normal (`ds11`) | 0.435 |
| อบลงไฟล์ (`x10`) | 0.370 |
| ทำซ้ำแถว (`rep10`) | 0.293 |
| ทำซ้ำ + ดันน้ำหนัก (`x10w`) | 0.293 |
| ทำซ้ำ ปิดน้ำหนัก (`rep10_nw`) | 0.272 |
| ทำซ้ำ + down (`rep10_ds11`) | 0.228 |

และ **การปิดน้ำหนักคลาสไม่ได้แก้ปัญหา** — `rep10_nw` (0.272) กับ `rep10_ds11` (0.228)
ซึ่งได้สมดุล 1:1 เป๊ะโดยไม่ต้องพึ่งน้ำหนักเลย กลับแย่กว่า `rep10` ที่เปิดน้ำหนัก (0.293)
**สมมติฐานเรื่อง "น้ำหนักถูกเจือจาง" จึงอธิบายได้ไม่หมด**

คำอธิบายที่เหลือ (ตีความ): การทำซ้ำแถวทำให้ 1 epoch มี gradient step มากขึ้น 1.8 เท่า
ด้วยข้อมูลชุดเดิม -> โมเดลจำเคสยากได้เร็วขึ้น -> early stopping ตัดจบเร็วขึ้น ->
ยังไม่ทันเรียนรู้ pattern ทั่วไป สังเกตได้จาก `ds11` ซึ่งเป็นวิธีเดียวที่ **ลด** จำนวนแถว
แทนที่จะเพิ่ม และเป็นวิธีขยายสมดุลตัวเดียวที่ยังรักษา mild ไว้ได้ใกล้เคียง `orig`

**โจทย์ binary ยังคงดีกว่า multiclass อย่างมากในการตรวจจับ** — mild recall
0.511 (binary/orig) เทียบกับ 0.370 (multiclass ที่ดีที่สุด) และ severe = 1.000

## 26. การแก้ข้อสรุปจากภาคก่อนหน้า

### 26.1 แก้หัวข้อ 12.2 — ข้อห้าม flip / scale / elastic ผิด

ตารางในหัวข้อ 12.2 ที่ระบุว่า flip แนวนอน / flip แนวตั้ง / scale / elastic
"ห้าม" **ไม่ถูกต้อง** ผลจริงจากหัวข้อ 21 คือชุดที่มี transform เหล่านี้อยู่ครึ่งบน
ของตารางทั้งหมด และ `shape` ล้วนๆ ชนะทุกชุดที่ปฏิบัติตามข้อห้าม ยกเว้น `strong`

ข้อความที่ถูกต้องควรเป็น: transform ที่แตะรูปทรงบิด label จริงในทางทฤษฎี แต่ในทาง
ปฏิบัติที่ระดับข้อมูล 8,409 ใบและปัญหาหลักคือ overfit **ประโยชน์ในฐานะ regularizer
มากกว่าความเสียหายต่อ label** — ยกเว้นเมื่อใช้ร่วมกับชุดที่รบกวนเรขาคณิตแรงอยู่แล้ว
ซึ่งจะถึงจุดอิ่มตัว (หัวข้อ 21 ข้อ 3)

### 26.2 แก้สมมติฐานหลักเรื่อง destripe

ภาคที่ 2 หัวข้อ 13.2 สรุปว่า "destriping ต่อยอดได้อีก" และเขียน `destripe_clahe`,
`destripe_unsharp`, `destripe_flatten` ขึ้นมาบนสมมติฐานนั้น

ผลจากหัวข้อ 20: **ทุกตัวที่ขึ้นต้นด้วย `destripe_` อยู่ครึ่งล่างของตารางหมด**
รวมทั้งอยู่ต่ำกว่า `destripe` เดี่ยวๆ และต่ำกว่าตัวที่เอาไปต่อท้ายเมื่อใช้เดี่ยวๆ ด้วย
(เช่น `destripe_flatten` 0.608 < `flatten` 0.647)

destripe ยังมีคุณค่าจริงในแง่ AUC (สูงสุดในกลุ่ม 0.937) แต่ **การเอาไปต่อหน้าตัวอื่น
ทำลายประโยชน์ ไม่ได้เสริม**

### 26.3 ยืนยันหัวข้อ 13.5 — macro F1 ไม่เหมาะกับงานนี้

ภาคนี้ให้หลักฐานเพิ่มอีก 2 ชิ้น:
- หัวข้อ 21: `strong_shape` ชนะ `strong` ทุกตัวชี้วัดที่เกี่ยวกับการตรวจจับ แต่แพ้ macro F1
- หัวข้อ 25.4: อันดับตาม macro F1 กลับหัวกับอันดับตามจำนวนผู้ป่วยที่ปล่อยหลุด

**ข้อเสนอสำหรับการเขียนเล่ม**: รายงาน macro F1 ไว้เพื่อเทียบกับงานอื่น แต่ใช้
**mild recall + จำนวนที่ปล่อยหลุด** เป็นตัวชี้วัดหลักในการตัดสินใจ และประกาศเกณฑ์นี้
ไว้ก่อนดูผลเสมอ

### 26.4 ตอบหัวข้อ 6.6 ครบแล้ว

"ยังไม่ได้ทดสอบ augmentation และ image preprocessing" — ตอบครบแล้วในภาคนี้
กวาด preprocess 10 แบบและ augment 8 แบบ อย่างละ 2 seed

## 27. ข้อจำกัดของภาคที่ 3-4

### 27.1 การทำซ้ำได้ยังไม่ถูกแก้ (สำคัญที่สุด)

ตามหัวข้อ 22.1 — config เดียวกัน seed เดียวกัน ให้ผลต่างกันได้ถึง 3.9 pp
ซึ่งใหญ่กว่าส่วนต่างระหว่างเงื่อนไขส่วนใหญ่ในภาคนี้ **ต้องแก้ก่อนเขียนเล่ม**
โดยตั้ง `random.seed` / `torch.cuda.manual_seed_all` / `cudnn.deterministic` /
`use_deterministic_algorithms` แล้วรันคู่ที่ซ้ำกันใหม่เพื่อยืนยัน

### 27.2 สอง seed ยังน้อยเกินไปสำหรับตารางอันดับ

ด้วย sd ที่วัดได้ 0.010–0.032 การมี 2 จุดต่อเงื่อนไขทำให้ประมาณ sd ได้หยาบมาก
ตารางหัวข้อ 20 และ 21 จึงเชื่อได้เฉพาะอันดับ 1 กับอันดับท้ายสุด ไม่ควรอ้างอันดับ
กลางตาราง — ควรมี 3-5 seed ก่อนลงเล่ม

### 27.3 กวาดทีละแกน ยังไม่ใช่ full grid

Part A ตรึง `augment = strong` · Part B ตรึง `preprocess = destripe` แล้วจับผู้ชนะ
มารวมกัน วิธีนี้ดีกว่า greedy ของภาคที่ 2 แต่ยังสมมติว่าสองแกนไม่มีปฏิสัมพันธ์กัน
สังเกตว่า Part B ตรึงไว้ที่ `destripe` ซึ่งภายหลังพบว่าไม่ใช่ผู้ชนะ (`flatten` ชนะ)
อันดับ augment จึงวัดบนฐานที่ไม่ใช่ฐานที่ดีที่สุด

### 27.4 ยังไม่ได้ทำ Grad-CAM กับโมเดลของภาคนี้

ยังค้างจากหัวข้อ 15.3 — ยังไม่ได้ตรวจว่าที่ดีขึ้นมาจากเหตุผลที่ถูกต้องหรือไม่
โดยเฉพาะกับชุด `*_shape` ที่บิดรูปทรง ซึ่งควรตรวจเป็นพิเศษ

### 27.5 ยังไม่ได้ลดหรือปรับ learning rate ในฝั่งชุด 10x

อาการพีคที่ epoch 3-5 ตรงกับกรณี lr สูงเกินสำหรับจำนวน step ต่อ epoch ที่มากขึ้น
แต่ยังไม่เคยลอง 1e-5 — เป็นคำอธิบายที่ยังไม่ถูกตัดออก

### 27.6 ข้อจำกัดของโจทย์ binary ที่ยังเหมือนเดิม

macro F1 ของโจทย์ binary (0.83-0.85) เทียบกับ multiclass (0.59-0.65) โดยตรงไม่ได้
เพราะเป็นค่าเฉลี่ยจาก 2 คลาสกับ 4 คลาส (ข้อจำกัดเดิมจากหัวข้อ 6.5)

## 28. บทเรียนเชิงระบบที่ได้จากภาคนี้

### 28.1 PyTorch บน Windows ไม่รอดจาก sleep/resume ถ้า `num_workers > 0`

worker ตาย โปรเซสหลักค้างรอตลอดกาล **ไม่มี error ไม่มี timeout** จอง VRAM ไว้เฉยๆ
— **เสียเวลาไป 41 ชั่วโมงเพราะเรื่องนี้**

**วิธีตรวจว่าค้างหรือไม่**: วัด CPU ซ้ำ 3 ครั้ง ถ้าตัวเลขไม่ขยับเลย = ค้าง
(อย่าดู timestamp ของ `best.pt` เพราะมันเขียนเฉพาะตอนโมเดลดีขึ้น ไม่ได้เขียนทุก epoch)

```bash
for i in 1 2 3; do powershell -NoProfile -Command "(Get-Process python -EA 0 | Sort-Object CPU -Descending | Select-Object -First 1).CPU"; done
nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader
```

GPU ควรอยู่ 90%+ ตอนเทรนจริง ถ้า 1-5% ทั้งที่จอง VRAM ไว้เยอะ = ค้าง

**วิธีป้องกัน**: ตั้งให้ปิดฝาโน้ตบุ๊กแล้วไม่หลับเฉพาะตอนเสียบปลั๊ก (ตอนใช้แบตยังคง
เป็น Sleep โดยตั้งใจ กันแบตหมดกลางคัน) และ **อย่าถอดปลั๊กระหว่างเทรน**

```powershell
# ตั้ง: ปิดฝาแล้วไม่หลับ (เฉพาะตอนเสียบปลั๊ก)

powercfg /setactive SCHEME_CURRENT
```

### 28.2 บั๊ก CRLF ทำให้ล้ม 3 รันรวด

Python บน Windows พิมพ์ CRLF โดยปริยาย เมื่อ shell script รับชื่อรันผ่าน
command substitution จะได้สตริงที่มี CR ติดท้าย ทำให้หา config ไม่เจอ
แก้โดยใส่ `sys.stdout.reconfigure(newline=chr(10))` ในทุกสคริปต์ที่พิมพ์ค่าให้ shell อ่าน

### 28.3 UnicodeEncodeError เมื่อ redirect output ลงไฟล์ (ย้ำจาก 15.5)

ต้องตั้ง `PYTHONIOENCODING=utf-8` ก่อนรันเสมอเมื่อจะเก็บ log — ทุก `run_*.sh` ตั้งให้แล้ว

### 28.4 ต้องใช้ `./.venv/Scripts/python.exe` เสมอ

พิมพ์ `python` เฉยๆ จะชี้ไป virtualenv ของโปรเจกต์อื่นที่ไม่มี `timm`

### 28.5 ห้ามแก้ไฟล์ใน `src/` หรือ `scripts/` ระหว่างที่มีการเทรนรันอยู่ (ย้ำจาก 15.5)

Windows ใช้ `spawn` ซึ่ง re-import โมดูลใหม่ทุก epoch worker ที่เกิดหลังแก้ไฟล์
จะได้โค้ดเวอร์ชันใหม่ที่ไม่ตรงกับ object ที่ถูก pickle ส่งไป

### 28.6 ตัวขับงานควรออกแบบให้ "ล้มแล้วไปต่อ" ตั้งแต่แรก

ทุก `run_*.sh` ในภาคนี้ข้ามรันที่มี `metrics.json` แล้ว ทำให้กด Ctrl-C หรือเครื่อง
ค้างกลางคืนแล้วรันคำสั่งเดิมซ้ำได้ทันที ไม่ต้องแก้สคริปต์ และสลับฟันปลาทีละ seed
(s42 ของทุกเงื่อนไข -> s43 ของทุกเงื่อนไข) เพื่อให้หยุดกลางทางเมื่อไหร่ก็ยังได้คู่ที่
เทียบกันได้

| ลำดับ | สิ่งที่ทำ | เหตุผล |
|---|---|---|
| 1 | **แก้เรื่องการทำซ้ำได้** — ตั้ง `random.seed` / `cuda.manual_seed_all` / `cudnn.deterministic` / `use_deterministic_algorithms` แล้วรันคู่ที่ซ้ำกันใหม่ | หัวข้อ 22.1 — noise 3.9 pp ที่ seed เดียวกันใหญ่กว่าส่วนต่างที่เรากำลังเทียบ ทุกข้อสรุปในเล่มขึ้นกับข้อนี้ |
| 2 | **เก็บเคส mild เพิ่ม 224 -> 500+ ปล้อง** | หัวข้อ 24 — ทางเดียวที่แก้ตรงเพดานจริง ทุกวิธีอื่นถูกลองแล้ว |
| 3 | **ใส่ปล้องข้างเคียงเข้ามาในกรอบ crop** | Genant ตัดสินโดยเทียบกับปล้องข้างเคียง แต่ masked crop ลบตัวอ้างอิงนั้นทิ้ง ข้อมูลที่จำเป็นอาจไม่ได้อยู่ในกรอบตั้งแต่ต้น |
| 4 | **รัน `flatten` + `strong_shape`** (ยังไม่เคยรวมกัน) | ผู้ชนะทั้งสองแกนถูกเลือกจากฐานคนละตัว (หัวข้อ 27.3) และ `strong_shape` ชนะทุกตัวชี้วัดที่เกี่ยวกับการตรวจจับ |
| 5 | **ordinal regression แทน 4-class softmax** | grade มีลำดับในตัว (0<1<2<3) ทายพลาด 1->2 ควรถูกลงโทษน้อยกว่า 1->0 — ค้างมาตั้งแต่ภาคที่ 1 |
| 6 | **Grad-CAM กับโมเดลของภาคที่ 3** โดยเฉพาะชุด `*_shape` | หัวข้อ 27.4 — ตรวจว่าที่ดีขึ้นมาจากเหตุผลที่ถูกต้อง ไม่ใช่ shortcut |
| 7 | **ปรับ lr ในฝั่งชุด 10x เป็น 1e-5** | หัวข้อ 27.5 — คำอธิบายเดียวที่ยังไม่ถูกตัดออกสำหรับอาการพีคที่ epoch 3-5 |
| 8 | **เพิ่ม regularization ตัวอื่น** (weight_decay 0.01-0.05, `drop_path_rate`) | weight_decay ปัจจุบัน 1e-4 ต่ำมากสำหรับ AdamW และยังไม่เคยเปิด stochastic depth เลย |
| 9 | **รัน RAD-DINO แบบ fine-tune เต็ม** | ค้างมาตั้งแต่ภาคที่ 1 — ยังไม่ได้ทำ |
